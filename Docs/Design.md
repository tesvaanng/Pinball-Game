## 0.3 核心設計原則 ⭐

> ### 核心機制要完整，數值要微小。
> ### 輔助機制可以是解鎖項，因為它們不參與核心循環，所以不會造成空轉。

| 類別 | 定義 | 能不能當肉鴿解鎖項？ | 本專案的例子 |
|---|---|---|---|
| **核心機制** | 拿掉它，遊戲不成立 | ❌ **不行** | 瞄準、力度、球上分數、充能條、逐發開火、傷害、怪物 |
| **輔助機制** | 拿掉它，核心循環照樣成立 | ✅ **可以** | 主動技能（拍打／磁力／慢動作）、多球／連發、當選模式 |

**解鎖的合法性條件：**

> **被解鎖的東西，不能是「已經在累積卻不生效的資源」。**

- ❌ 壞的解鎖：前期分數沒用，拿到遺物才有用 → 前三層空轉，玩家覺得被騙
- ✅ 好的解鎖：前期沒有技能，拿到技能後多一個決策維度 → 純粹的獲得

**判斷標準**：把第 1 層單獨抽出來，它是不是一個完整的小遊戲？如果是，基礎玩法就對了。

## 0.4 設計支柱

1. **每一發都要有期待感** —— 從按下到結算不超過 8 秒，過程中有「看得懂的數字在長大」
2. **構築必須改變盤面行為**，不只是改數字
3. **數字要大得囂張，但規則要極簡** —— 玩家只需要懂「加法 → 乘法 → 指數」三段
4. **數字必須有後果** —— 分數經充能條變成逐發開火，決定你能不能活過這層
5. **一局 20–35 分鐘**，節點式推進，隨時可中離

# 第 1 章 核心循環

## 1.1 一句話

> **瞄準方向 ＋ 拉力度 → 球從盤面頂部射出 → 打釘累積「球上分數」→ 落袋時乘上袋口倍率 → 分數灌進充能條 → 每滿一條就逐發開火 → 對盤外的怪物造成傷害。**

## 1.2 完整管線

```
① 玩家瞄準方向（滑鼠即時轉向）＋ 拉力度（0–100%）
        ↓
② 球從盤面「頂部中央」的發射器射出 → 瞄準決定方向、力度決定初速
        ↓
③ 球在盤面彈跳
        ├─ 每碰到一顆釘子 →「球上分數」+= 釘子分數（飄字跟著球累加）
        └─ 球落袋 / 超時
        ↓
④ 結算：顯示「球上分數 × 袋口倍率」= 本球結算分數
        （超時則倍率視為 1×）
        ↓
⑤ 結算分數灌進「充能條」——**溢出無損**，直接累積到下一條
        ↓
⑥ 每滿一條充能上限 C → 開火一次
        （子彈從充能條射出，逐發、有間隔；充能條演出「充滿→歸零→充滿」）
        一顆球的分數可能觸發 0 次、1 次、或連續多次開火
        每次開火：傷害 = 固定值 D
        ↓
⑦ 盤外的怪物 HP −= 傷害
        怪物死亡 → 立即停止開火（防鞭屍），剩餘能量全部保留
        ↓
⑧ 回合數 +1；重複 ①
        已發射的球全部落袋後，本層才結束
```

## 1.3 一顆球的完整生命週期

| 階段 | 玩家看到 | 玩家在想 |
|---|---|---|
| 瞄準＋拉力度 | 槍口朝滑鼠轉、力度條（含書籤刻度） | 「上次 60% 從左邊進去彈了很久，這次往右一點試試」 |
| 出手 | 球從頂部射出 | 「再彈一下、再彈一下…」 |
| 球打釘 | 飄字跟著球累加 | 「撐住！再彈一下！」 |
| 球落袋 | 顯示 `球上分數 × 倍率` | 「3×…還不錯」 |
| 充能結算 | 分數飛進充能條 | 「差一點就滿了」 |
| 開火 | 子彈逐發從充能條射出、怪物 HP 下降 | 「再一發！再一發！」 |
| 下一顆 | 剩餘球數、怪物剩餘 HP | 「我還剩 5 顆，還差 31 傷…」 |

## 1.4 名詞定義（本文件全文通用）

| 名詞 | 定義 |
|---|---|
| **球上分數** | 單顆球在飛行中，靠打釘累積的分數。**尚未兌現** |
| **結算分數** | `球上分數 × 袋口倍率`。球落袋時產生，是本球的最終價值 |
| **袋口倍率** | 底部每個袋口各自的倍率（例：1×、5×、20×） |
| **充能條** | 累積「結算分數」的計量條。**跨球、跨層累積**，滿一條就觸發一次開火 |
| **充能上限** | 充能條的容量 `C`。滿了就開火並扣除一個 `C` |
| **溢出** | 結算分數超過當前充能條的部分。**溢出無損**，直接推進到下一條（可能一次推進好幾條） |
| **殘量** | 本層結束時充能條上未滿一條的能量。**保留到下一層**（例外見 2.5.8） |
| **每次開火傷害** | **固定常數 `D`**。滿一次充能上限就造成 `D` 點傷害。**基礎版與充能上限無關** |
| **傷害** | 一次開火造成的傷害 = `D` |
| **怪物** | 每層的目標。**位於盤面之外**，只能被開火傷害 |
| **玩家 HP** | 跨層保留的資源。每一輪的球用完後被怪物攻擊，歸零即失敗 |
| **一輪** | 8–10 顆球的循環。球打完 → 怪物攻擊 → 補滿球數（見 2.5.9） |

## 1.5 三層架構（概念分層，非程式強制）

```
┌─ 第 3 層：Run 層
│   樓層節點 → 戰鬥 → 獎勵 → 商店 → … → Boss
│   持有：RunState（種子、樓層、遺物、球、資源、怪物 HP）
│
├─ 第 2 層：規則 / 計分層 ★ 肉鴉修改的就是這層
│   輸入：打釘事件、落袋事件
│   輸出：球上分數、結算分數、充能、傷害
│   固定管線：基礎值 → 加法 → 乘法 → 獨立乘 → 指數/連擊 → 暴擊 → 觸發
│
└─ 第 1 層：物理 / 表現層（Unity）
    球、釘子、發射器（瞄準）、力度條、鏡頭、粒子、音效、飄字
    只負責「產生事件」與「播放結果」，不含任何規則
```

> ⚠️ **這是概念分層，不是程式分層。** 實際程式以 **Manager** 分層（4.4、`Assets/Script/ARCHITECTURE.md`）。
> **v1.3 已決定不加 asmdef**，所以「規則不碰 Unity」現在是**自律**而非編譯器強制。
> 但仍建議把結算數學寫成**不讀 `Transform` 的純函式**——那是免費的，將來要抽出來時會省很多事。

# 第 2 章 基礎玩法規格

## 2.1 輸入

玩家有**兩個輸入**：瞄準方向、發射力度。

| # | 問題 | 決定 |
|---|---|---|
| 2.1.1 | 玩家控制什麼 | **① 瞄準方向**（滑鼠即時轉向槍口）＋ **② 發射力度（0–100%）**——按住蓄力、放開發射 |
| 2.1.2 | 球在飛時玩家能做什麼 | **什麼都不能做**。干預手段（拍打／磁力／慢動作）是**肉鴉解鎖項** |
| 2.1.3 | 瞄準決定什麼 | **球射出的方向**。發射器在盤面**頂部中央**，預設朝下；滑鼠位置決定槍口指向，限制在相對預設方向 **±80°** 內（`Launcher.maxAimAngle`） |
| 2.1.4 | 力度決定什麼 | **球的初速**——`AddForce(direction × shootForce × power01)`。初速決定球帶多少能量進盤面 → **彈多久、彈多遠 → 球上分數的高低** |
| 2.1.5 | 有沒有擋板 | ❌ 沒有 |
| 2.1.6 | 有沒有預測線 | ❌ 沒有。**永不加入**（見 2.1.7） |

> **兩個輸入的分工必須記住**：**瞄準決定「去哪裡」，力度決定「去得多猛」。**
> 兩者都會影響結果，但影響的方式不同——這是 v1.3 之後技術成分的來源。

### 2.1.7 為什麼有瞄準，卻沒有預測線

瞄準與「懸念」並不衝突，衝突的是**預測線**。

| 有預測線 | 只有瞄準（本專案） |
|---|---|
| 可以預覽牆壁反彈 → 能算出會進哪個袋 → **懸念消失，遊戲變成解謎** | 你只能決定「往哪個方向、用多大的力丟出去」→ 丟出去之後**依然不可控** |

> **原則：瞄準決定「輸入」，不決定「結果」。中間那段混沌必須留給盤面。**

> ⚠️ 這一條是 v1.3 改回瞄準時**唯一保留的紅線**。
> 當初 `Decision-Log` 2.1 反對瞄準的理由③是「預測線洩漏太多」——**不是反對瞄準本身**。
> 只要不給預測線，那條理由就不成立。

### 2.1.8 學習輔助（M1 才做）

玩家要學會「瞄準角 × 力度 ↔ 落點」的對應，需要的不是預測線，而是**結果的回饋**：

| 工具 | 內容 | 排程 |
|---|---|---|
| **幽靈試投** | 免費試投，看軌跡不計分、不消耗球 | **M1** |
| **落點熱區顯示** | 盤面底部淡色顯示「歷史落點分布」 | **M1** |

> ⚠️ **已知風險**：M0 沒有這兩者，玩家只能用真實的球（每層 8–10 顆）試錯。
> 而且輸入是**二維**（角度 × 力度），比 v1.2 的一維力度更難靠自己摸索。
> 若 M0 的「瞄準＋力度學習」驗收（驗收 #1）過不了，**第一個要補的就是幽靈試投**，而不是改盤面。

### 2.2.3 為什麼廢掉「進場層」（v1.3）

原本的「4 進場層」定義是：**球沿右側軌道爬升，力度決定脫離高度 → 從哪一層切入盤面**。

改成頂部中央發射器之後，**球不再「爬軌道」，而是直接被射進盤面**——這個概念失去了物理基礎，留著只會讓後面的盤面設計綁手綁腳。**整節廢除。**

技術成分改由兩個輸入承擔：

| 輸入 | 影響 |
|---|---|
| **瞄準方向** | 球從哪個方向進入盤面、先撞到什麼 |
| **發射力度** | 球帶多少能量進去 → 彈多久、彈多遠 → 球上分數 |

> ⚠️ **這是有代價的，要記在帳上：**
> 1. 輸入從**一維變二維**，學習難度上升（`Decision-Log` 2.1 的理由②原本是「力度比瞄準更容易統計驗證」）
> 2. 舊設計靠「軌道高度」天然地把「力度」視覺化，那個免費的教學消失了
> 3. 盤面必須從頭設計，好讓**兩個輸入各自都有意義**（見 2.2.4、6.1）
>
> **這是 6.1 從「未定」變成「重新設計」的直接原因。**

### 2.2.4 盤面必須有「結構」⚠️

> **均勻的 Plinko 釘子網格，會讓「瞄準」與「力度」同時失去意義。**

原因：Plinko 網格的設計目的就是**消除輸入的影響**——不管從哪裡丟、用多大的力，結果都是同一條常態分布。
但這裡要的正好相反：**讓兩個輸入都能被玩家感覺到**。

**已確認的結論**：盤面要**保留 Plinko 的視覺與手感**，但必須加入**結構元素**（分區擋板、漏斗、密度差異），且**結構只佔盤面 5–10% 的面積**——90% 看起來還是 Plinko，但那 10% 決定遊戲有沒有技術成分。

**已識別的陷阱**：

| 陷阱 | 為什麼是陷阱 |
|---|---|
| 「空曠區」直通高倍率袋口 | 它變成必勝路線，取捨消失 → **原則：「空曠」的代價必須是「不可控」，不是「又快又好」** |
| **發射器正下方一路暢通**（頂部中央發射新增的陷阱） | 玩家會發現「閉著眼睛往下打」是最佳解，兩個輸入同時失效 |
| 只有瞄準有意義、力度沒差 | 力度條變成裝飾 → 兩軸掃描會抓到（見 6.1） |
| 只有力度有意義、瞄準沒差 | 那就退化成 v1.2 的一維設計，瞄準是多餘的 → 不如拿掉 |

> **設計目標：發射器正下方必須是最平庸的路線。好路線必須要「瞄準 ＋ 力度」配合才進得去。**

> **v1 例外**：6.1.1 的第一版盤面**刻意**用均勻網格，當作量測的基準線。
> 那是**已知會違反本節原則**的版本，目的是量出「沒有結構」的落點分布，用來對照後面的結構版。

## 2.4 計分與充能（完整規則）

### 2.4.1 結算公式

```
打釘：      球上分數 += 釘子分數
落袋：      結算分數 = 球上分數 × 袋口倍率      ← 顯示這個數字
            充能條 += 結算分數                  ← 溢出無損，直接推進到下一條
超時：      結算分數 = 球上分數 × 1             ← 超時以 1 倍結算

充能條 >= 充能上限 C 時，重複：
            充能條 -= C
            傷害 = D                      ← 固定值，與 C 無關
            怪物 HP -= 傷害
            若怪物已死 → 停止開火（防鞭屍），剩餘充能保留
```

### 2.4.2 ⭐ 開火模型：連續累加器（重要）

**開火發生在「球落袋結算之後」，不是飛行途中。** 開火是純粹的「充能條 → 怪物」，與球無關。

**充能條是一條連續累加器**，不是「每球歸零的計量條」：

```
充能條 += 結算分數          ← 溢出無損
while 充能條 >= C:
    充能條 -= C
    開火一次
```

| 上一球留下的殘量 | 本球結算分數 | 結果 |
|---|---|---|
| 0.6 條 | 0.7 條 | 開火 **1** 次，殘量 0.3 條 |
| 0 條 | 2.0 條 | 開火 **2** 次，殘量 0 |
| 0 條 | 3.5 條 | 開火 **3** 次，殘量 0.5 條 |
| 0 條 | 0.2 條 | 開火 **0** 次，殘量 0.2 條 |

**所以「開火幾次」完全由玩家該球賺到多少分決定**，跟球數無關。這帶來三個結果：

| 結果 | 說明 |
|---|---|
| **爆走感是基礎玩法自帶的** | 一顆爆分球可以在一瞬間連續清空怪物——不需要肉鴉 |
| **期待與 payoff 分家** | 落袋 ＝ 期待（未知 × 倍率）；充能爆開 ＝ payoff（唰唰唰打 N 下） |
| **「提高 `C`」是純減益** | 每發傷害固定，`C` 變大就只是「更慢、更少次」，沒有補償 |

#### 開火的呈現：逐發、可數

- 每滿一條 `C` → **一顆子彈從充能條射出**，飛向怪物
- 充能條演出 **充滿 → 歸零 → 充滿 → 歸零**，一次一條
- 子彈一個接一個，**間隔約 0.15 秒**——玩家要能數得出來打了幾下

> **為什麼要「可數」**：特殊怪物會有「每受擊 N 次觸發反擊」這類機制（見 3.3.4）。若開火是一次性爆發，玩家無法把「打了幾下」和敵人的反應對應起來。

> **「同時爆發／光柱」是肉鴉的多發流派**（見 3.2.1），不是基礎玩法。

#### 開火次數的上限

**沒有硬上限。** 一顆球想開 50 次就開 50 次。用**特效分級**避免畫面失控：

| 次數 | 演出 |
|---|---|
| 1–3 次 | 逐發演出，每發完整可見 |
| 4–10 次 | 逐發演出，間隔縮短 |
| 10 次以上 | 聚合演出（渲染成連續光柱＋數字狂跳），但**傷害結算仍然逐發** |

> **⚠️ 沒有上限的後果**：如果 `C` 固定不變而分數指數成長，後期一顆球可能開火數百次。這是 6.4 的核心問題——**M0 先用固定 `C` 驗證手感，平衡階段再處理**。

### 2.4.3 ⭐ 傷害模型與三個構築槓桿

**基礎版的傷害公式（這是本設計的核心）：**

```
每次開火傷害 D  = 固定常數（與充能上限無關）
開火次數        = 結算分數 / 充能上限 C
每球總傷害      = (結算分數 / C) × D
```

**三個可以被構築修改的槓桿，全部都直接影響總傷害：**

| 槓桿 | 動它會怎樣 | 玩家感受 | 對敵人機制的價值 |
|---|---|---|---|
| **結算分數 ↑** | 更多能量 → 更多開火 | 「分數跳更快」 | 中性（單發與次數同時放大） |
| **每次開火傷害 `D` ↑** | 每一發更痛 | 「數字變大了」 | **對「固定值護甲」有效**（單發大） |
| **充能上限 `C` ↓** | 同樣的分數切成更多發 | 「噠噠噠噠噠」 | **對「易傷疊層」有效**（次數多） |

> ⭐ **三者數學上都是「乘傷害」，但在敵人機制的語境下價值不同。** 這就是 build 深度的來源——見 3.3。

**⚠️ 三個槓桿都是乘法 → 這是「三重指數」**

```
總傷害 = 結算分數 × D / C
         └─ 軸 A ─┘  └B┘ └C┘
```

三個軸同時指數成長，比雙指數更難平衡。**這是本設計最大的數值風險**，必須用 headless 模擬（4.5）驗證到第 15 層。

**⚠️ `C` 有雙重身份，需要小心**

`C` 同時是：**設計者控制節奏的旋鈕**（要讓每球開火次數不爆走）與**玩家 build 的槓桿**（越小越強）。

| `C` 的處理方式 | 結果 | 問題 |
|---|---|---|
| **固定不變** | 後期 `結算分數` 成長 → 一球開火數百次 | 節奏失控、效能爆炸 |
| **隨樓層成長**（維持發數 0.2–5 次） | 節奏穩定 | 但 `C` 變大會**壓縮玩家傷害**，所以 `D` 必須同時成長補回來；且「設計者旋鈕」與「玩家槓桿」是同一顆 |

**→ 🔶 這個問題尚未定案**（見 6.4）。目前的傾向是「`C` 隨樓層成長，`D` 同步成長」。

**設計者要控制的兩個曲線（暫定）：**

| 要控制的東西 | 該動的數字 | 條件 |
|---|---|---|
| 開火節奏（不要爆走） | **充能上限 `C`** | `C ∝ 單球結算分數` |
| 難度 | **怪物 HP** | `HP ∝ 目標每球傷害` |

### 2.4.4 設計意圖：為什麼這個管線是好的

| 效果 | 說明 |
|---|---|
| **二階張力** | 球要**彈得久**（球上分數高）**且**要**落進高倍率袋**。這兩件事可能衝突 |
| **技術＝戰力** | 瞄準與力度選得好 → 球走的路徑好（打更多釘、落進高倍率袋） → 結算分數高 → 開火多 → 傷害高。**因果鏈完整** |
| **懸念** | 球快落袋時，玩家希望它「再彈一下」，因為每多彈一下就多一分機會讓充能條滿 |
| **袋口佈局＝盤面設計的全部** | 袋口倍率怎麼分布，直接決定這張圖好不好玩 |

### 2.4.5 飄字規格

| 規則 | 內容 |
|---|---|
| 出現 | 該球**第一次加分**時，在球的位置顯示飄字 |
| 累加 | 後續每次加分，**累加到同一個數字上**，飄字跟著球移動 |
| 隱藏 | 一段時間沒有加分 → 飄字**隱藏** |
| **重要** | **隱藏時球上分數仍在累積**，不是歸零。下次加分重新出現並顯示完整值 |

> ⚠️ **因為 2.1.2（球飛時玩家不能做事），飄字是玩家唯一的參與機制。** 它不是裝飾——**M0 就要做好，不能留到最後。**

## 2.5 結束、關卡流程與節奏

| # | 問題 | 決定 |
|---|---|---|
| 2.5.1 | 一顆球的壽命 | **落入袋口即結束** |
| 2.5.2 | 卡球／超時 | **超出一定時間 → 直接以 1 倍結算球上分數** |
| 2.5.3 | 一層幾顆球 | **8–10 顆 ＝ 一輪**。球打完 → 怪物攻擊 → **補滿再來一輪** |
| 2.5.4 | 一層的目標 | **在玩家 HP 歸零前把怪物 HP 打到 0**（消耗戰，不是回合上限） |
| 2.5.5 | 失敗條件 | **玩家 HP ≤ 0 → 本局結束**。**沒有回合上限** |
| 2.5.6 | 有沒有「輸」以外的評價 | 顯示本局總分與個人最佳 |
| 2.5.7 | **怪物死亡時** | **不立即結束本層**——等**已發射的球全部落袋**；**也不再投剩下的球** |
| 2.5.8 | **本層結束時的殘量** | **保留到下一層**；**例外：下一層是 Boss 房則清空** |
| 2.5.9 | **怪物何時攻擊** | 基礎：**每一輪的球全部落袋後攻擊一次**；特殊怪物另有額外機制（見 3.3.4） |
| 2.5.10 | **玩家 HP** | **跨層保留**，只在營火等節點恢復 |

### 2.5.2 為什麼「超時以 1 倍結算」很優雅

**一條規則同時處理三種狀況**：卡球、球無限彈跳、超時。
而且**不嚴厲**——分數保留，只是失去袋口倍率（相當於沒進任何袋）。

附加好處：它**天然獎勵短球**，抑制長球帶來的問題，與「無干預」互補。

### 2.5.8 ⭐ 層間充能保留與防鞭屍（重要）

這是「充能」能不能變成**可囤積資源**的關鍵。

| # | 規則 | 理由 |
|---|---|---|
| 1 | 怪物死亡 → **立即停止開火** | **防鞭屍**：剩下的十幾發打在一具屍體上，既浪費又荒謬 |
| 2 | 未發射的能量（**含整條滿管與零頭**）**全部保留到下一層** | 溢傷不該被丟棄 |
| 3 | 本層的球**全部落袋後**才結算 | 已經在飛的球不該被憑空取消 |
| 4 | **例外：下一層是 Boss 房 → 充能清空** | Boss 是一場乾淨的戰鬥，不能被前面囤積的能量直接跳過 |

**設計後果：完美構築可以「連通好幾層」**——一波充能連續清掉兩三個房間，直到 Boss 房把它清空。

> **這是本設計裡少數「主動產生爆走感」的規則，而且它完全長在基礎玩法上，不需要任何肉鴉遺物。**

> ⚠️ 這條規則讓「怪物 HP」的設計變得關鍵：太低 → 一顆爆分球連穿三層；太高 → 囤積沒有回報。**這是難度曲線的主控點。**

### 2.5.9 敵人攻擊時機與失敗條件（方案 B）

**基礎結構：一層 ＝ 一場消耗戰，玩家 HP 是燒著的爐子，怪物 HP 是你要打穿的牆。**

```
一輪：投 8–10 顆球
   ├─ 怪物死亡 → 本層結束（剩餘充能保留）
   └─ 怪物還活著 → 怪物攻擊玩家（玩家 HP −= 怪物攻擊力）→ 補滿球數，下一輪
```

| 層級 | 規則 |
|---|---|
| **基礎** | 每一輪的球全部落袋後，**怪物攻擊一次** |
| **特殊怪物** | 除基礎攻擊外，**另加自己的攻擊機制**。例：**每受擊 5 次觸發反擊** |

**失敗條件只有「玩家 HP ≤ 0」。沒有回合上限**——所以「回合用完怪物仍存活」不再是失敗，只是**怪物再打你一次**。

**為什麼這個結構好：**

| # | 理由 |
|---|---|
| 1 | 它讓「球數」變成**可以隨樓層調整的節奏旋鈕**，不需要動 `C` |
| 2 | **資源焦慮有地方落腳**：不再是「我還剩幾顆球」，而是「我還剩 30 HP，牠還有 500，這輪打不夠我就死」 |
| 3 | 玩家 HP 順便成為肉鴉層的新 build 軸（回血、減傷、吸血），而且**不干預核心循環**——是合法的輔助機制（0.3） |
| 4 | 它與 2.5.8 的層間保留相乘，產生「用一波囤積扛過危險樓層」的策略 |

> **特殊怪物的攻擊機制屬於肉鴉層**（見 3.3.4）。基礎玩法只需要「球打完 → 怪物攻擊」這一條。

### 2.5.11 節奏建議值

| 維度 | 建議 | 理由 |
|---|---|---|
| 單球總時長 | **3–8 秒** | 玩家沒事做，時間必須短 |
| 每秒碰撞次數 | **3–6 次** | 飄字是主要參與機制 → 數字要一直在跳 |
| 投球間隔 | **1–2 秒** | 讓玩家有時間決定下一次瞄準與力度 |

> ① 和 ② 連動：球飛 5 秒、每秒 4 次碰撞 ≈ 每顆球 20 次加分。這是飄字爽感的下限。

## 3.1 一局（Run）的結構

```
起始 → [ 節點地圖 ] → Boss → 下一層 → … → 第 8 層 Boss → 通關 / 失敗
         ├ 戰鬥   ├ 精英   ├ 商店   ├ 事件   ├ 寶箱   └ 營火
```

- **線性樓層 ＋ 節點分歧**（Slay the Spire 風），不是開放地圖
- 每層一個怪物；每層 **8–10 回合**
- 一局 20–35 分鐘

### 解鎖節奏（前期的權力曲線）

| 遊戲進度 | 玩家擁有 |
|---|---|
| **第 1 層** | 只有核心循環：瞄準、力度、球上分數、充能、開火、傷害 |
| **第 2–3 層** | ＋ **當選模式（簡化版）** ← 爽感脈衝，讓玩家早點看到天花板 |
| **第 3 層＋** | ＋ 遺物賦予的主動技能（拍打等）、改造、數值放大 |

> **設計意圖**：核心機制從第一天就有；**輔助機制逐層解鎖**。每一層都有一個「新玩具」，權力曲線更陡，而且不會造成空轉（見 0.3）。

## 3.2 build 槓桿（肉鴉放大核心循環）

### 3.2.1 三個傷害軸 + 一個形態軸

| 軸 | 基礎值 | 構築後 | 玩家感受 | **被什麼懲罰** |
|---|---|---|---|---|
| **A：結算分數** | 釘子 1 分 | 連擊複利、倍率釘、低摩擦讓球活更久 | 「分數跳更快」 | —（中性放大器） |
| **B：每次開火傷害 `D`** | 固定值 | ×5、×20… | 「每發更痛」 | **溢傷**（擊殺邊界浪費） |
| **C：充能上限 `C`** ⭐ | 常數 | **調低** → 同樣分數切成更多發 | 「噠噠噠噠噠」 | **適應裝甲**（懲罰頻率） |
| **D：攻擊形態** | 單體一擊 | 多段／擴散／持續／全體 | 「換一種打法」 | 各形態有各自的場合 |

> **注意：`C` 是「只有往下調才有意義」的軸。** 在新模型裡 `D` 固定，所以提高 `C` 只會讓傷害變少——沒有玩家會想提高它。`C` 的成長曲線是**設計者的節奏旋鈕**，不是玩家的選項（見 2.4.3）。

> **「多發流派」**：基礎玩法的開火是**逐發、可數**的（2.4.2）。肉鴉可以把它改造成**同時爆發**（光柱、數字狂跳、一次結算全部子彈）——這是高頻流派專屬的視覺獎勵，也是「同時爆發」當作解鎖項的落點。

### 3.2.2 三個傷害軸如何互相取捨 ⭐

三個軸**數學上都是「乘傷害」**，所以如果沒有敵人機制，它們會只是「哪個數字大選哪個」。
**敵人機制就是讓它們產生情境差異的東西**（見 3.3）：

| 槓桿 | 自然優勢 | 自然的代價 |
|---|---|---|
| **提高 `D`**（每發更痛） | 對「固定值護甲」有效——大單發被吃掉的比例小 | **溢傷**：怪物剩 5 HP 時開一發 100 傷，浪費 95 |
| **調低 `C`**（更多發） | 對「易傷疊層」有效——次數多，疊層快 | **適應裝甲**：敵人每次受擊後續傷害遞減，次數多反而吃虧 |
| **提高分數** | 兩個都放大，而且是唯一會讓「球上分數」這個大數字變大的軸 | 只影響開火，不影響單發大小或次數結構 |

**這三個軸構成 build 深度的主體：玩家要判斷「這一局我該堆哪一個」，而答案取決於他遇到什麼敵人。**

## 3.3 敵人機制（讓三個傷害軸產生情境差異）

> **三個傷害軸數學上都是「乘傷害」。如果沒有敵人機制，玩家就只會算出「哪個數字大」然後永遠選它——build 就死了。**
> 有它們，同一個軸在不同房間有不同價值，**這才是肉鴉**。

### 3.3.1 三個機制

| 機制 | 規則 | 利好 |
|---|---|---|
| **固定值護甲** | `實際傷害 = max(傷害 − 護甲, 傷害 × 0.10)` | **提高 `D`**（大單發被吃掉的比例小） |
| **適應裝甲** | 敵人每受到一次傷害，後續受到的傷害遞減 15% | **提高 `C`**（次數少） |
| **易傷疊層** | 每次受擊疊 1 層（+5% 受傷），持續 2 秒；2 秒內沒再受傷則清空 | **調低 `C`**（次數多） |

> ⚠️ **護甲必須是「固定值減免」，不能是「百分比減免」。**
> 百分比減免對所有大小的傷害一視同仁 → **不產生任何取捨**。
> 固定值減免讓小單發被吃掉大比例、大單發被吃掉小比例 → **這才獎勵「提高 `D`」**。
> 例：護甲 30：40 傷 → 10 傷（25% 有效）；200 傷 → 170 傷（85% 有效）。

> ⚠️ **不要用「硬護甲門檻」**（傷害 < 護甲 → 0 傷害）。因為指數成長會讓玩家在拿到某個升級的**瞬間**從「完全打不動」跳到「直接輾過」，中間沒有過渡帶。
> **軟護甲的 10% 下限是必需的**——它是「完美構築可以一定程度強打」能否成立的唯一保證。

### 3.3.2 敵人位置：盤面之外 ✅

**怪物位於盤面之外**，只能被開火傷害。球不能攻擊怪物。

- 優點：**盤面幾何全程不變**（球的落點分布穩定），盤面設計完全可控，架構乾淨
- 球的唯一工作就是**賺分**——`球 → 分數 → 充能 → 開火 → 怪物`，鏈條單一清楚

### 3.3.3 房間選擇的前提

- **每個怪物都要「打得過」，但對不同流派的效率差 2–3 倍**
- ❌ 若硬性區分「高頻流才能打」和「大傷流才能打」，得到的不是構築選擇，而是**路線選擇**，玩家會被迫鎖死在單一流派
- **地圖必須預先顯示敵人類型**，否則這不是決策，是盲賭

### 3.3.4 怪物攻擊機制（肉鴉層）

基礎版只有「球全部落袋後攻擊一次」（見 2.5.9）。以下是**特殊怪物**可以附加的攻擊機制：

| 機制 | 規則 | 針對什麼 build |
|---|---|---|
| **受擊反擊** | 每受擊 N 次觸發一次反擊（例：每 5 次） | **懲罰高頻流**（調低 `C`、多段攻擊）會被反擊更多次 |
| **蓄力** | 每回合蓄力，N 回合後釋放大攻擊 | 逼玩家在時限內解決（變相 DPS 檢定） |
| **再生** | 每回合回復固定 HP | 懲罰「剛好打不死」的構築，獎勵一次性爆發 |
| **護盾** | 有獨立的護盾條，要先打穿 | 獎勵大單發（提高 `D`） |
| **階段變化** | HP 降到 50% 時改變機制 | 讓長戰鬥有節奏 |

> ⚠️ **「受擊反擊」與「易傷疊層」是直接衝突的兩個機制**：前者懲罰次數多，後者獎勵次數多。兩者同時出現時，玩家必須判斷哪一邊的數值更關鍵——**這正是 build 深度的來源**（見 `Decision-Log.md` 第四部分原則 11）。

## 3.4 當選模式（爆發結構）⭐

柏青哥的原生情緒曲線，也是「大數字」的情緒高點：

```
球落入【啟動落袋】→ 期待值累積（可見計量條＋堆疊音效）
    → 期待值滿 → 【當選】8 秒內：
         所有結算分數 ×50、發射不消耗球數、盤面機關全開
    → 當選期間再次觸發當選 → 【連莊】，倍率複利（×50 → ×250 → …）
    → 連莊結束 → 一切歸零，玩家渴望下一次
```

| 階段 | 內容 |
|---|---|
| **M0** | **不做**（M0 只做核心循環） |
| **M1 起** | 簡化版：1 個啟動落袋、期待值滿 → 固定 8 秒 ×50、**不做連莊複利** |
| **M3** | 完整版：連莊複利、機關全開、球自動分裂 |

**它是輔助機制**（拿掉它核心循環照樣成立），所以可以當解鎖項。

## 3.5 主動技能（肉鴉解鎖項）

**初始沒有技能。** 技能透過遺物獲得（見 0.3 的解鎖合法性）。

### 三個基礎技能

| 技能 | 效果 | 用途 |
|---|---|---|
| **拍打 Nudge** | 對所有正在下落的球施加水平推力 | 救回即將落入低倍率袋的球 |
| **磁力脈衝** | 3 秒內指定半徑內的球被吸引向指定位置 | 把球導向啟動落袋或高倍率袋 |
| **集中／慢動作** | 3 秒內 `timeScale = 0.3` | 操作精度的放大器 |

### 設計原則（違反任何一條就不做）

1. **必須是有限資源**（次數不跨層累積），否則玩家無腦連放，操作深度歸零
2. **必須與盤面互動**（改變球的軌跡），不能只是「+50 分」——加數字交給遺物
3. **必須能被遺物改造**（+次數、強化效果、技能連動），這樣技能本身也是 build 軸

**「時機」從哪來？** 不需要額外 UI——來自**盤面機關**（旋轉桿、開合閘門在動），**放開力度（出手）的時機**決定球能否穿過開著的閘門。

### M3 之後再擴充
追加投球（立即再發一顆、不消耗回合）、時光回溯（重放本球）、技能連動（拍打觸發磁力）。

## 3.6 內容的資料模型

用「觸發／條件／動作」的資料模型組出遺物，而不是每個遺物寫一個 class：

```csharp
public enum TriggerKind { OnHit, OnBounce, OnPegDestroyed, OnShotStart, OnShotEnd, OnBallLost, OnScoreGain }
public enum ActionKind  { AddFlat, AddPercent, AddIndependentMultiplier,
                          MultiplyCombo, SpawnBall, AddPeg, ApplyMark, GrantCurrency }

[Serializable] public struct EffectDef
{
    public TriggerKind Trigger;
    public ConditionDef[] Conditions;   // HasTag("Bumper") / EveryNth(10) / SpeedAbove(8)
    public ActionDef[]    Actions;
    public int            MaxTriggersPerShot;   // 防爆保險
}
```

**好處**：新增 40 件遺物＝填表，不寫程式；平衡調整＝改數字。

## 3.7 盤面（關卡）生成

**手做 chunk ＋ 種子化拼裝 ＋ 驗證器**。不要純程序生成——物理盤面的難度變異太大，會產出「球必卡死」或「一發通關」的盤面。

```
Board = 3~5 個手工 chunk（入口／中段／出口）由 MapStream 選序組裝
驗證器（編輯器工具）：投放 200 次隨機球，檢查
  - 卡球率 < 1%
  - 得分分布標準差在可接受區間
  - 每次投球最終都能抵達出口
```

## 3.8 存檔

**快照式**（非操作日誌式）——因為物理不可複現，日誌式重播行不通。存檔粒度＝節點結束，允許中離。

```json
{
  "saveVersion": 1,
  "runSeed": 8823749182391,
  "floor": 4, "nodeIndex": 2,
  "score":    { "m": 1.234, "e": 47 },
  "currency": { "m": 3.1,   "e": 6  },
  "relics":  ["relic_bumper_echo", "relic_crit_overflow"],
  "balls":   [{ "id": "ball_heavy", "level": 3 }],
  "counters": { "hitsThisRun": 18422, "critsThisRun": 903 },
  "rngStates": { "map": 1234567, "reward": 7654321 }
}
```

**規則**：只存字串 id，**永不存 ScriptableObject 參照或索引**；從 v1 就帶 `saveVersion` 與遷移函式。

## 3.9 跨階段引擎（肉鴉的核心爽感來源）

前面幾節的機制大多是**放大器**——它們讓數字變大。**引擎**不一樣：它們把一個系統的輸出接到另一個系統的輸入，產生**自我加速的循環**。

> **大數字遊戲的爆走感來自引擎，不是來自放大器。**
> 放大器只是讓「同樣的循環」跑出更大的數字，玩家第三層就習慣了。引擎會讓循環**自己加速**，成長曲線本身在變化——這才是「停不下來」的來源。

| # | 引擎 | 循環 | 實作難度 |
|---|---|---|---|
| **G1** | **傷害 → 充能回饋** | 造成傷害 → 回充能 → 更多開火 → 更多傷害 | 低 |
| **G2** | **開火 → 盤面** | 開火在盤面上炸出洞／生成釘子 → 下一球得分更高 → 更多開火 | 中 |
| **G3** | **分數 → 當選期待值** | 結算分數同時累積當選計量 → 更容易開當選 → ×50 → 更多分數 | 中 |

> 三者都是**肉鴉層**的東西，不進基礎玩法。

### 3.9.1 分數軸的三個「獨特互動」候選

**問題**：`結算分數`、`D`、`1/C` 三個軸在數學上都是「乘一個純量」。後兩者已經有敵人機制給它們情境差異（3.3.1），但**分數軸沒有**——它只是「兩個都放大」。

**解法**：讓分數**同時驅動別的東西**，使它不只是傷害的一個乘數。

| 候選 | 內容 | 評價 |
|---|---|---|
| **A. 分數 → 當選期待值** | 結算分數同時累積當選計量條 | ⭐ **推薦**——與 3.4 綁在一起，兩個系統互相強化，不需要新資源 |
| **B. 分數 → 貨幣** | 結算分數同時轉成商店貨幣 | 產生「要傷害還是要經濟」的取捨 |
| **C. 分數 → 形態解鎖** | 單球結算分數超過門檻 → 該次開火升級為擴散／全體 | 分數變成「解鎖條件」而非純數值 |

> **⚠️ 三個都是肉鴉層的東西**，不進基礎玩法。
> 基礎玩法裡三個軸確實等價——**這是刻意的**：**基礎玩法是純技巧遊戲，肉鴉層才是數字遊戲。**

# 第 4 章 工程建議（大部分可延後）

## 4.1 BigNumber ⭐ 建議第一天就用

若第一版用 `int` 寫分數，等到要支援 `1e87` 時，要改幾百處的加減乘除、UI 綁定、存檔格式。

只要一開始就把分數／貨幣／倍率型別定義成 `BigNumber`（struct ＋ 隱式轉換），`score += 5;` 這種程式碼完全不用改。**成本約 200 行、半天。**

`mantissa (double) × 10^exponent (int)`，正規化為 `mantissa ∈ [1,10)`。所有運算 O(1)。

**型別分工（很重要）：**

| 用途 | 型別 | 原因 |
|---|---|---|
| 分數、貨幣、總倍率 | `BigNumber` | 無上限 |
| 命中次數、連擊數、庫存計數 | `int` / `long` | 需要精確。`BigNumber` 加 1 到 1e30 會直接消失 |
| 機率、百分比、速度 | `float` / `double` | 不需要大數，而且「10%」用 `BigNumber` 無法表示 |

**必要配套**：加法時若指數差 > 17 直接回傳較大者；`Exponent` 要 clamp（避免 int 溢位變負數 → 分數變 0）；`ToDisplayString()` 支援 `K/M/B/T/aa/ab…` 與科學記號；**格式化不要在 hot path 做**。

## 4.2 決定性 RNG

不用 `UnityEngine.Random`（全域狀態、無法分叉、無法存檔回復）。自寫 `DeterministicRng`（xorshift64*，只有一個 `ulong state`）。

**分流設計**——每個用途一條獨立流，互不干擾：

| 流 | 用途 | 為什麼要獨立 |
|---|---|---|
| `MapStream` | 地圖生成 | 玩家在商店多按一次不該改變地圖 |
| `RewardStream` | 獎勵三選一 | 同上 |
| `ShotStream` | 每發球的判定 | 可重播單一發球 |
| `CosmeticStream` | 粒子、音效變體 | **絕不能影響玩法判定** |

**注意**：不要嘗試讓物理決定性（跨機器不可能穩定）。改成「物理自由，但隨機判定全部走可複現的 RNG」。

## 4.3 觸發佇列必須有預算上限

「A 觸發 B，B 觸發 A」在長專案裡一定會發生，而且通常發生在玩家 build 成形的爽點上——當掉最傷。

**做法**：每發球最多處理 N 步（例：512），超過就靜默丟棄，並在開發版印警告。

## 4.4 分層（v1.3：以資料夾與命名空間分層，**不用 asmdef**）

> **v1.3 決定：追認現況。** 不加 Assembly Definition。
> 理由、代價、以及放棄了什麼，見 `Decision-Log` 2.17。這一節記錄**現在實際遵守的規則**。

**現況結構**（實際存在於專案中）：

```
Assets/Script/
├── Core/      BigNumber、DeterministicRng、Singleton、初始化介面與註冊表
├── Data/      GameConfigSO、LevelConfigSO、DataManager
├── Health/    Health、HealthManager
├── Scoring/   ScoringManager、ChargeMeter
├── Combat/    Monster 家族、CombatManager
├── Board/     BoardManager、BallController、Peg、Pocket、Launcher
├── Input/     InputManager、PowerGauge
├── UI/        BattleUIManager
└── Flow/      BattleManager、SetupManager
```

**分層規則**（取代 asmdef 的自律版，完整版見 `Assets/Script/ARCHITECTURE.md`）：

| # | 規則 |
|---|---|
| 1 | 其他範疇只能用該範疇的 **Manager**，不直接呼叫它內部的小工具類別 |
| 2 | `BattleManager` 是**唯一**同時協調多個 Manager 的地方 |
| 3 | Manager 之間盡量**單向依賴** |
| 4 | 全部使用 `Pinball.*` 命名空間 |

### 4.4.1 這個決定放棄了什麼 ⚠️

| 放棄 | 後果 |
|---|---|
| **編譯器強制**「規則不碰 Unity」 | 紀律從**強制**降級為**自律**——寫錯不會有人擋你 |
| **規則層可脫離 Unity 執行** | 直接影響 4.5 的 headless 模擬做法 |
| Console 專案引用規則層跑測試 | 規則測試只能在 Unity 內跑（EditMode Test 仍可用，但會連 Unity 一起載入） |

> **仍然建議保留的免費習慣**：結算數學（`ChargeMeter`、`BigNumber`、傷害計算）
> 盡量寫成**不讀 `Transform` / `GameObject` 的純函式**。
> 不必搬資料夾、不必加 asmdef，但這樣做之後，**將來真要抽出來會容易得多**。
> 這是免費的選項；不做，將來要付利息。

## 4.5 為什麼最終需要「headless 模擬」

**大數字遊戲的平衡沒辦法用手玩調出來。** 需要能跑 10,000 場、驗證到第 15 層。

> **v1.3 變更**：原本這裡寫的是「規則程式碼必須能不開 Unity 執行——這就是 4.4 的理由」。
> 4.4 已改成不用 asmdef，**那條路沒了。但需求還在**，只是做法要換。

| 做法 | 內容 | 評價 |
|---|---|---|
| ~~A. 純 C# 規則層 ＋ Console 專案~~ | 規則不依賴 Unity，用 `.csproj` 直接跑 | ❌ **v1.3 放棄**（前提是 4.4 的 asmdef） |
| **B. Unity batch mode** | `Unity.exe -batchmode -nographics -executeMethod` 執行模擬腳本 | ✅ **現在唯一確定可行**。慢、要授權、CI 較麻煩，但能動 |
| **C. 盤面機率化** | 不模擬物理，把盤面抽象成「落點分布」，餵給結算邏輯 | ✅ **效率最高**，但前提是**結算邏輯能被單獨呼叫**——現在散在 Manager 裡，要先整理 |

> ⚠️ **這是 v1.3 決定的真實代價，要記在帳上。**
> M3 的「headless 10k 場模擬報表」與 5.3 的「三重乘法失衡驗證到第 15 層」都依賴這件事。
> **動 M3 之前必須先解決**，否則那兩張驗收會開天窗。
>
> 到時候**最小的工作**是：把 `ChargeMeter` 與傷害結算整理成**可單獨呼叫的純函式**（做法 C 的前提），
> 而**不是**把整層搬出來、更不是回頭補 asmdef。

**驗證方法**：因為輸入是**二維**，要做**兩次一維掃描**，兩次都必須過。

| 掃描 | 做法 | 通過標準 |
|---|---|---|
| **瞄準掃描** | **固定力度**（例如 60%），瞄準角分 5 檔，每檔投 20 次 | 每檔落點明顯集中，且**彼此分開** |
| **力度掃描** | **固定瞄準角**（例如正下方偏左 15°），力度分 5 檔，每檔投 20 次 | 每檔落點明顯集中，且**彼此分開** |

> **判讀方式**：
> - 某一軸的 5 檔幾乎重疊（都接近同一條常態分布）→ **那個輸入是死的**，盤面結構失敗，重做。

>   而不是留著一個騙人的力度條或瞄準。

### 6.1.1 v1：**刻意**選的平均分佈（基準線）

第一版盤面**不做任何結構**，就是均勻的 Plinko 網格。這不是偷懶，是流程的一步：

| # | 理由 |
|---|---|
| 1 | **先有基準線**：要知道「完全沒有結構」長什麼樣，才知道結構該加多少 |
| 2 | **量測工具需要東西可量**：沒有盤面，兩軸掃描根本沒得開發 |
| 3 | **預期它會失敗**——2.2.4 已經說了均勻網格會讓兩個輸入同時失去意義。**兩軸掃描失敗，就是 v1 成功的證明** |

**實作位置**：`Assets/Script/Board/BoardLayout.cs`（資料）＋ `BoardBuilder.cs`（生成器）。

盤面是**資料**而不是手擺的場景物件，因為 6.1 的流程是「生成 → 量測 → 改 → 再量」，會跑很多次。
生成出來的物件帶 `HideFlags.DontSave`，**不會寫進場景檔**——盤面的唯一真相是 `BoardLayout` 資產。

**v1 參數**（世界座標；盤面內部 30 × 30，中心 `(0, -3.97)`，與場景中的 `Manchine Body` 一致）：

| 參數 | 值 | 依據 |
|---|---|---|
| 球直徑 | **0.6** | 球 prefab：scale 0.6 × collider radius 0.5 |
| 釘子間距 | **1.5** | 球直徑的 2.5 倍 |
| 釘子半徑 | **0.2** | 間距 − 2×半徑 = 1.1 > 球直徑 0.6，球過得去 |
| 欄 × 排 | **19 × 17**（約 315 顆） | 由間距與邊距推導 |
| 邊距 | 上 3、下 1.5、左右各 1.5 | 上邊距必須大於球半徑＋釘子半徑，否則球一出生就疊在釘子上 |
| 袋口 | **8 個**，3.45 × 1.19 | 附錄 A.2 的倍率 20/8/3/1/1/3/8/20 |

> ⚠️ **量測前必須先處理的兩個干擾源**（都在 `BoardManager.ShootBall`）：
> 1. `spawnOffSet`（預設 **0.5**）會給每次發射一個隨機橫向偏移。**同一個瞄準角丟 20 次，每次落點都不一樣**——量測時必須把它設成 0，否則量到的是雜訊。

> 另外 `BallController.OnCollisionEnter2D` 目前**每碰一次就加分**，沒有 B.4 坑 1 說的「同一顆釘子 N 毫秒內只算一次」的冷卻。球貼著釘子滑動時分數會重複累加，這也會污染量測。

## A.4 一顆球

```
1. 玩家輸入：瞄準方向 A（滑鼠，相對預設方向 ±80°）＋ 力度 P ∈ [0, 1]
2. S_ball ← 0，計時器 t ← 0
3. 球在盤面上飛行：
     每碰到一顆釘子 → S_ball += 釘子分數
     t += dt
4. 結束條件（先發生者為準）：
     a. 球進入袋口 k  → 倍率 M ← Pocket[k]

```

## A.5 結算與充能

```
E += S                          ← 溢出無損

while E >= C:
    E -= C
    if 怪物已死: break           ← 防鞭屍
    怪物 HP -= D
    產生一次「開火事件」（供演出用）
```

- `E` **跨球、跨層累積**（2.5.8）
- **開火次數沒有上限**（2.4.2）
- `E` 可以是小數（例如 0.6 條）

## A.6 一輪

```
while 剩餘球數 > 0:
    剩餘球數 -= 1
    投一顆球（A.4）→ 結算與充能（A.5）
    if 怪物已死: goto A.7

# 這一輪的球全部用完，怪物還活著
玩家 HP -= 怪物攻擊力
if 玩家 HP <= 0: goto A.8

剩餘球數 ← B                     ← 補滿
輪數 += 1
if 輪數 > 最大輪數: goto A.8     ← 防呆
回到 A.6 開頭
```

```
4. 玩家 HP 不恢復                         ← 回血是營火節點的事
5. 進入節點地圖 → 下一層
```

## A.9 邊界情況（實作時必須處理）

| 情況 | 規則 |
|---|---|
| 一顆球的分數讓 `E` 跨過好幾條 `C` | **逐條開火**，每次獨立結算；怪物中途死亡就停止 |
| 怪物死亡時 `E` 還有整條滿管 | **全部保留**到下一層 |
| 下一層是 Boss 房 | `E` **在進入前**歸零 |
| `S_ball = 0`（沒打到釘子就落袋） | 合法。`S = 0`，不開火 |
| 球超時 | 以 **1×** 結算，不是 0 |
| 玩家 HP 扣到負數 | **夾在 0** |
| 怪物 HP 扣到負數 | **夾在 0** |
| `C <= 0` | **未定義**。設定時必須保證 `C > 0` |
| 同一次開火的溢出傷害 | 不處理，直接扣（這是 3.2.1 的「溢傷」） |
| HP 因浮點誤差停在**極小的正值**（例如 `2.2e-16`） | **視為 0**。死亡判定用**相對容差**：`HP ≤ maxHp × 1e-9` → 死亡，並把 HP **夾成剛好的 `0`**（見 `Decision-Log` 2.15） |
| UI 拿到極小的非零值 | **禁止印成 `0`**：`0 < value < 0.01` 一律用科學記號（`2.2e-16`）。「0」只能有一個意思 |
| 同一次開火要扣 N 次血 | **不可合併成 `hp -= damage × N` 一次算完**。逐發結算（本表第一列）與 3.3.4「受擊反擊」都依賴「被打幾次」 |

## B.1 現況架構：Manager 分層，不是「物理／規則分離」

> 原本這一節叫「唯一不能妥協的架構決定：把物理和規則切開」。
> **v1.3 已經放棄那個要求**（見 4.4 與 `Decision-Log` 2.17）。以下是現在實際的狀況。

**實際的架構**：以**範疇**分層，每個範疇有一個 Manager 當對外窗口。

| 範疇 | Manager | 職責 |
|---|---|---|
| Core | （無 Manager） | BigNumber、DeterministicRng、Singleton、初始化介面與註冊表 |
| Data | `DataManager` | GameConfigSO、LevelConfigSO |
| Health | `HealthManager` | 玩家與怪物共用的血量 |
| Scoring | `ScoringManager` | 結算分數、充能條、開火次數 |
| Combat | `CombatManager` | 怪物、傷害、怪物攻擊 |
| Board | `BoardManager` | 盤面、球、釘子、袋口、發射器 |
| Input | `InputManager` | 瞄準、力度條 |
| UI | `BattleUIManager` | 分數、充能、HP |
| Flow | `BattleManager` / `SetupManager` | 初始化、一層的戰鬥流程 |

**這個架構沒有提供的保證**（原本要靠 asmdef 拿到的）：

| 原計畫的保證 | 現況 |
|---|---|
| 規則不碰 Unity，寫錯會**編譯失敗** | ❌ 沒有強制，**只能靠自律** |
| 結算邏輯可以脫離 Unity 跑 | ❌ 做不到（見 4.5） |
| 物理與規則各有各的測試方法 | 🔶 都只能在 Unity 內測 |

> **所以：** 下面的 B.3、B.4 仍然是**正確且重要**的實作紀律，
> 只是它們現在**靠人記住**，而不是靠編譯器擋。

## B.2 一條單向的資料流

即使沒有拆成兩個組件，**資料流仍然必須是單向的**。

```
   物理（Unity）
   球、釘子、發射器、碰撞、重力
        │  事件：碰釘 / 落袋 / 超時
        ▼
   Manager 層
   ScoringManager 結算分數 → ChargeMeter 充能 → CombatManager 扣怪物 HP
        │  結果：結算數字 ＋ 逐發開火清單
        ▼
   表現層（Unity）
   飄字、粒子、鏡頭、音效、HP 條
```

> ⚠️ **結算邏輯不可以反過來問「球現在在哪」。**
> `ScoringManager.SettleBall(ballScore, multiplier)` 收到的必須是**已經算好的數字**，
> 不可以自己去讀 `BallController` 的位置或速度。
> 一旦破例，結算就綁死了當下的畫面狀態——**B.3 的「結算與演出分開」會立刻失效**。

## B.3 一個 frame 的順序（最容易做錯的地方）

**開火的「結算」和「演出」必須分開。**

```
物理步
  └─ 碰撞回呼 → 產生「碰釘事件」

規則
  └─ 球落袋 → 呼叫結算 → 結算「瞬間」算完：
       結算分數、充能、開火 N 次、怪物 HP 扣完
       → 回傳一個「開火清單」（N 筆）

表現
  └─ 照著清單播：第 1 顆子彈飛出去（0.15s）→ 第 2 顆 → …
       ⚠️ 此時怪物 HP 早就扣完了，所以畫面上的 HP 條要「追」上去
```

| ❌ 錯誤做法 | ✅ 正確做法 |
|---|---|
| 用 Coroutine 邊播動畫邊扣血 | 規則一次算完，演出照著清單播 |
| 狀態與演出綁死 | 狀態是即時的，演出是延遲的 |

**為什麼正確做法是對的：**

| 好處 | 說明 |
|---|---|
| **跳過演出變成免費功能** | 玩家按加速 → 清單一股腦播完，**狀態不用重算** |
| **不會有「演出播到一半存檔」的鬼狀態** | 存檔永遠是結算後的乾淨狀態 |
| **結算完全不管時間** | 它的時間是「步」，不是「秒」 |

**代價**：需要一組「視覺數值」（HP 條、充能條、總分）去 lerp 追上真實數值。這是標準做法，而且它讓數字看起來更爽（滾動感）。

## B.4 五個已知的坑

### 坑 1：Unity 的碰撞回呼不是「一次碰撞」

`OnCollisionEnter2D` 在球貼著釘子滑動、或高速穿透時，觸發的次數跟你以為的不一樣。**直接把它當「碰到一顆釘子」，分數會爆走或漏算。**

**對策**：在球的層級記錄「這顆球最近碰過哪些釘子、什麼時候」。同一顆釘子在 N 毫秒內重複命中只算一次。
**這個冷卻時間是「手感數值」**（寫進 2.6），不是規則。

### 坑 2：超時該由誰判定

超時是**規則**（A.4 的條件 b），但它需要「時間」。

**對策**：由結算邏輯自己累加 `dt`（或把 `dt` 當參數傳進去），**不要直接讀 `Time.time`**。
理由：`Time.timeScale` 會被慢動作技能改變（3.5），那時「8 秒超時」該不該跟著變慢是**設計問題**——把時間的來源握在結算邏輯手上，之後才有得選。

### 坑 3：`BigNumber` 用錯地方

`BigNumber` 是給**會指數成長的東西**用的。**次數、計數、索引不要用它**——`BigNumber` 加 1 到 1e30 會直接消失。

| 用 `BigNumber` | 用 `int` / `long` |
|---|---|
| 球上分數、結算分數、充能、怪物 HP、傷害 | 碰釘次數、球數、輪數、袋口索引 |

**還有**：`ToDisplayString()` 會產生字串，**不要在 Update 裡每幀呼叫**（4.6）。

### 坑 4：太早做抽象

3.6 的「觸發／條件／動作」資料模型很漂亮，但**那是 M1 的事**。
M0 如果先做它，你會為了「以後可能用得到」而扭曲現在的程式，然後在真正需要時發現它設計錯了。

> **M0 的程式碼應該醜。** 用 `if`、用直接呼叫、用寫死的值。**規模到了再抽象。**

### 坑 5：先做美術

盤面幾何（6.1）還沒定，美術一定會重做。**M0 用純色方塊與圓形就好。**

## B.5 建議的實作順序：垂直切片，不是水平分層

**❌ 水平分層**：先把「球」做到完美 → 再做「釘子」→ 再做「計分」。
→ 你會花一週做出一顆很漂亮的球，然後發現整個循環不成立。

**✅ 垂直切片**：**先讓一條最醜、最完整的管線跑通。**

| 階段 | 目標 | 這一階段「故意不做」的東西 | 現況 |
|---|---|---|---|
| **0. 骨架** | 球從上方落下、碰釘加分、落底結算、Console 印出「球上分數 × 倍率 → 充能 → 開火 N 次 → 怪物 HP」 | 瞄準、力度、袋口倍率、飄字、美術 | ✅ 已有對應實作（`BigNumber`、`ChargeMeter`、`CombatManager`） |
| **1. 循環** | 充能條、逐發開火、怪物 HP、一輪 8 顆球、怪物攻擊、玩家 HP、層間保留 | 輸入、盤面結構 | 🟡 大致有（`HealthManager`、`BattleManager`）；**層間殘量保留／防鞭屍待確認** |
| **2. 輸入** | 頂部中央發射器＋滑鼠瞄準、力度條 | 飄字、音效 | ✅ 已有（`Launcher`、`PowerGauge`） |
| **3. 表現** | **飄字**（全專案最高優先）、逐發開火演出、數字滾動 | 美術、音效 | ❌ **未做**——目前只有 `BattleUIManager` 的靜態文字 |
| **4. 量測** | **瞄準掃描 ＋ 力度掃描**（各 5 檔 × 20 次，見 6.1） | — | ❌ **未做**，而且**現在最該做**（見 B.7） |

> 註：「現況」這一欄是根據 `Assets/Script/` 的檔案清單與 `ARCHITECTURE.md` 判讀的，
> **不是逐行驗證過的**。要當成事實使用前請先確認。

> **關鍵**（與 v1.2 相同，仍然成立）：階段 0 結束時，遊戲應該**邏輯上完整、但完全不好玩**。
> 那是最理想的狀態——因為從那之後，每一次改動都只影響一個局部。

## B.8 驗證策略：兩種東西，兩種方法

| | 結算邏輯 | 物理／盤面 |
|---|---|---|
| 怎麼驗證 | **單元測試**（確定性、快） | **統計量測**（分布、慢） |
| 在哪裡跑 | Unity Test Runner（EditMode） | 實機場景 |
| 什麼時候跑 | 每次改動 | 每次改盤面 |
| 通過標準 | 附錄 A.9 的每一條都對 | **瞄準掃描與力度掃描：兩軸各 5 檔 × 20 次，落點都明顯集中且彼此分開**（6.1） |

> ⚠️ **不要試圖對物理寫單元測試。** 物理不可複現，那條路走不通——
> 這也是為什麼 6.1 的驗收是**統計量測**而不是斷言。

> **v1.3 註**：原本這裡假設結算邏輯可以不載入 Unity 就跑。
> 現在做不到（4.4），所以測試會**連 Unity 一起載入**——比較慢，但 EditMode Test 仍然可用，
> **附錄 A.9 的每一條都還是值得寫成測試**。

## B.9 一句話總結

> **把「結算」寫成「收到數字、吐出新數字」的東西；Unity 只負責產生事件與播放結果。**

如果整個實作只記得一句話，就是這一句。

> **v1.3 註**：原本的版本是「先把規則寫成一個不需要 Unity 也能跑的東西」。
> 那個**組件層級**的要求已經放棄了（4.4）。
> 但這句話的**精神還在**——就算不搬資料夾、不加 asmdef，
> **結算邏輯也不該去讀 `Transform` 或 `BallController` 的當下狀態**。
