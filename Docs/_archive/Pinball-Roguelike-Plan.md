# 彈珠肉鴿（Roguelike Big-Number Pinball）初步方案

> 專案：`W:\unity\unity project\Pinball Game`
> 環境現況：Unity 2022.3.45f1 / Input System 1.7.0 / Cinemachine 2.10.7 / TextMeshPro 3.0.6 / UGUI
> 目前資產：3D 灰盒場景（`Machine`、`Shooter`、`shootPoint`）、`ball.prefab`、`BallShooter.cs`
> 文件版本：v0.2（設計題 T1–T6 已全數定案；核心攻擊模型確立）

---

## 0. 一句話定位

**用柏青哥的「物理投球」當操作層，用肉鴿的「配球 × 遺物」當構築層，用「盤面賺分數、分數換傷害」當大數字引擎。**

**核心循環（一句話）：**
> 投球 → 盤面賺分數 → **充能** → **滿格自動開火：能量 × 轉換率 ＝ 傷害** → 打倒敵人 → 拿獎勵 → 重複

**第 1 層（零構築）就已經是完整的這個循環，只是數值極小。肉鴿構築放大它，而不是解鎖它**（第 17 節）。

操作提供手感與隨機性，構築提供策略與重玩性，大數字提供成長快感——而**分數→傷害的轉換，是把這三者綁在一起的那根軸**（第 16 節）。三者必須分層解耦，這是本方案最重要的一條原則。

參考座標（同類作品）：

| 作品 | 借鏡什麼 | 不借鏡什麼 |
|---|---|---|
| [Peglin](https://www.pixelatedplaygrounds.com/bookclub/peglin-ballioniare) | 釘子＝敵人的 HP 化、盤面即武器 | 瞄準式操作（本作只用力度）、數值成長偏保守 |
| [Ballionaire](https://www.rockpapershotgun.com/ballionaire-the-physics-roguelike-in-which-you-build-pachinko-boards-drops-on-december-10th) | 遺物連鎖的爽感、物理的觀賞性 | 擺盤式構築（本作 T1 已定案為固定盤面） |
| Balatro | 倍率曲線、稀有度／資源經濟、Stake 難度層 | 純卡牌，無物理手感 |
| 放置遊戲（Idle） | BigNumber、格式化解法、通膨曲線 | 無操作的掛機本體 |

差異化空間（T1–T6 定案後）：**「同一座固定盤面，用不同的球與遺物打出完全不同的分數曲線，再把分數換成傷害。」** 三條軸互相獨立——力度（操作）、配球（構築）、轉換率（成長）——這是純卡牌遊戲與純擺盤遊戲都給不了的組合。

## 1. 設計支柱（Design Pillars）

1. **每一發都要有期待感** —— 從按下到結算不超過 5 秒，過程中有「看得懂的數字在長大」。
2. **構築必須改變盤面行為**，不只是改數字。遺物應該讓玩家用不同方式打球（**轉化釘子**、改物理常數、生成機關、分裂球、標記釘）。
3. **數字要大得囂張，但規則要極簡** —— 玩家只需要懂「加法 → 乘法 → 指數」三段。
4. **數字必須有後果** —— 分數不是排行榜，它經轉換率變成傷害，決定你能不能活過這一層（第 16 節）。這是大數字遊戲能不能成立的關鍵。
5. **一局 20–35 分鐘**，節點式推進，隨時可中離（存檔粒度＝節點）。

## 2. 核心循環（三層架構）

```
┌─ 第 3 層：Meta / Run 層（純 C#，可存檔、可模擬）
│   地圖節點 → 選獎勵 → 商店 → 事件 → Boss → 下一層
│   持有：RunState（種子、樓層、累積分數、轉換率、遺物、球、資源、敵人 HP）
│   盤面命中時：分數 → 充能條；滿格自動開火 → 能量 × 轉換率 → 傷害（第 16、17 節）
│
├─ 第 2 層：規則 / 計分層（純 C#，決定性、可單元測試）★ 肉鴿修改的就是這層
│   輸入 HitEvent（球、釘子、速度、角度、第幾次彈跳）
│   輸出 ScoreDelta（BigNumber）＋觸發佇列（連鎖）
│   固定管線：基礎值 → 加法 → 乘法 → 獨立乘 → 指數/連擊 → 暴擊 → 觸發
│
└─ 第 1 層：物理 / 表現層（Unity）
    球、釘子、牆、發射軌道、力度條、主動技能、鏡頭、粒子、音效、飄字
    只負責「產生 HitEvent」與「播放結果」，不含任何規則
```

**鐵律：第 1 層永遠不呼叫第 2 層以外的地方改數字；第 2 層永遠不 `using UnityEngine`。**

> ⚠️ **這是「概念上的分層」，不是說你現在要開 asmdef。** 現在只要用資料夾分開 ＋ 一個習慣（規則類別不繼承 MonoBehaviour），asmdef 等 M2/M3 要跑平衡模擬時再加。**白話說明見 3.0。**

這條鐵律換來三個能力，都是肉鴿後期必需的：
- **Headless 模擬**：開一個 Console 專案跑 10,000 場，用程式調平衡，而不是用雙手玩。
- **決定性種子局**：每日挑戰、種子分享、Bug 重現。
- **單元測試**：遺物連鎖、BigNumber 邊界、存檔遷移。

## 3. 工程決策（D1–D6）

> ⚠️ **本節是工程建議，不是遊戲設計。** 其中 **D4（asmdef / 純 C#）是可選的優化，可以延後到 M2–M3 再做，現在完全不用碰。** 其餘（D1 物理維度、D3 BigNumber）建議早點定，因為晚改成本高。

### 3.0 先講清楚：asmdef 與「純 C#」是什麼，你需要嗎

**asmdef（Assembly Definition，組件定義檔）**
Unity 預設把你**所有**腳本編譯成**一個大組件**（`Assembly-CSharp`）。asmdef 讓你把某些資料夾**拆出來單獨編譯**。

| | |
|---|---|
| 好處 | 改一行只重編那一組（編譯快）；可強制「這組不准引用那組」（防架構亂掉） |
| 代價 | 要自己在 Inspector 管理引用關係，**設錯會出現很難懂的編譯錯誤** |

**「純 C# Core」＝ 不 `using UnityEngine` 的程式碼**
只用 C# 語言本身的東西（`class`、`struct`、`int`、`Math`），不碰 `GameObject`、`MonoBehaviour`、`Transform`、`Vector3`。

| | |
|---|---|
| 好處 | 這種程式碼**可以不開 Unity 就執行** → 單元測試秒級、可寫 Console 程式跑幾萬場模擬 |
| 代價 | 不能用 `Vector3`、`Mathf`、`Debug.Log` 這些方便的東西 |

**你需要嗎？只有一個真正的理由：**

| 你想做的事 | 需要嗎 |
|---|---|
| 把遊戲做出來、能玩 | ❌ **完全不需要** |
| 寫測試驗證計分公式 | 🟡 有幫助，但 Unity Test Runner 也能測 MonoBehaviour |
| **跑一萬場模擬來調平衡** | ✅ **需要** ← 唯一真正的理由 |
| 編譯快一點 | 🟡 專案小的時候差異不大 |

**實務建議（白話版）：**

1. **現在：什麼都不用設。** 只養成一個習慣：
   > **規則類別不要繼承 `MonoBehaviour`，不要碰 `Transform` / `GameObject`。**
   例如 `BigNumber`、計分公式、抽獎勵，寫成普通 `class`/`struct`，放 `Scripts/Rules/`。MonoBehaviour 再去呼叫它們。**這是一句話的習慣，不是技術。**
2. **等 M2/M3 真的要調平衡時**，再在那幾個資料夾按右鍵 → Create → Assembly Definition，Unity 會產生檔案，只要勾引用。**一小時內的事。**
3. **完全不想做也可以。** 代價是到 M3 想把規則從 MonoBehaviour 裡拔出來時要花幾天。**那不是災難，是延後付款。**

### 3.1 決策總表：哪些要早定，哪些可以延後

| # | 決策 | 建議時機 | 為什麼 |
|---|---|---|---|
| D1 | 物理維度（2D vs 3D） | **立刻** | 晚改＝重做所有盤面 |
| D2 | 隨機判定不依賴物理 | **立刻**（概念） | 影響架構，但實作很簡單 |
| D3 | `BigNumber` 從第一天用 | **立刻** | 晚改＝幾百處型別要換 |
| D4 | asmdef ＋ 純 C# Core | **⏳ 可延後到 M2/M3** | 只是為了跑平衡模擬。現在用資料夾＋習慣即可（見 3.0） |
| D5 | 資料驅動內容 ＋ id 式存檔 | **M1 之前** | 存檔格式一旦出貨就難改 |
| D6 | 計分管線順序寫死 | **M0** | 影響所有後續數值設計 |

### D1. 物理維度：模擬用 2D，呈現可 3D ✅ 已定案（配合柏青哥定位）

| 方案 | 優點 | 代價 |
|---|---|---|
| **A. 2D 物理模擬（Rigidbody2D）+ 2D/偽 3D 呈現** | 彈跳可控、幾乎不穿模、可支撐 200+ 球、好除錯 | 少了真 3D 的空間感 |
| B. 3D 物理但鎖軸（freeze Z、鎖 X/Y 旋轉） | 保留 3D 素材流程 | 需自行處理 CCD、球數上限低 |
| C. 完整 3D 物理 | 視覺最炫 | 彈珠台 3D 物理是出了名的 jank：穿模、卡死、不可重現，**與肉鴿所需的「大量球＋可驗證平衡」直接衝突** |

**建議 A**。目前灰盒是 3D，但現在改成本最低；等到有 20 個盤面、50 個遺物之後再改，等於重做。

> 若你堅持 3D 視覺：模擬層仍用 `Rigidbody2D` 在一個平面上跑，3D 模型只是「掛在」模擬位置上（球體貼圖、機器外殼、鏡頭用 Perspective + Cinemachine 做景深）。玩家分不出來，但你省下 80% 的除錯時間。

### D2. 物理驅動 vs 決定性模擬

**不要**嘗試讓物理決定性（跨機器不可能穩定）。改成：**物理自由，但「隨機判定」全部走可複現的 RNG。**

具體做法：暴擊、掉落、獎勵抽取不依賴物理事件順序，而用 `(runSeed, shotIndex, hitIndex)` 派生出來的計數器式 RNG。這樣即使球的軌跡每台機器都不同，**同一顆種子的「決策序列」仍可複現**——足以支撐每日挑戰與公平性。

### D3. BigNumber 必須從第一天就用 ⭐

若第一版用 `int` 寫分數，等到要支援 `1e87` 時，你要改的是幾百處的加減乘除、UI 綁定、存檔格式、比較運算子。

只要一開始就把分數／貨幣／倍率型別定義成 `BigNumber`（struct + 隱式轉換），`score += 5;` 這種程式碼**完全不用改**。成本：約 200 行、半天。回報：避免一次大重構。

**分工原則（很重要）：**

| 用途 | 型別 | 原因 |
|---|---|---|
| 分數、貨幣、總倍率 | `BigNumber` | 無上限 |
| 命中次數、連擊數、庫存計數 | `int` / `long` | 需要精確，`BigNumber` 加 1 到 1e30 會直接消失 |
| 機率、百分比、速度、角度 | `float` / `double` | 不需要大數 |

> 這個分工是很多大數字遊戲翻車的地方：把「每 10 次命中觸發一次」的計數器做成 BigNumber，當分數變成 1e40 時計數器精度崩掉，遺物直接壞掉。

### D4. 分層 ＋ 純 C# Core Assembly ⏳ **可延後（M2/M3 再做）**

> **這不是必做項。** 現在你只需要「資料夾 ＋ 一個習慣」，asmdef 等真的要跑平衡模擬時再加。理由與白話說明見 **3.0**。

**核心概念：把「遊戲規則」和「Unity 物件」分開。**

| 層 | 內容 | 規則 |
|---|---|---|
| **規則層** | `BigNumber`、計分公式、觸發、抽獎勵、地圖生成 | **普通 `class`/`struct`，不繼承 `MonoBehaviour`，不碰 `Transform`/`GameObject`** |
| **表現層** | 球、釘子、鏡頭、粒子、音效、飄字、UI | MonoBehaviour，呼叫規則層 |

**你現在唯一要做的事**：建立資料夾，並養成上面那一條習慣。

```
Assets/Scripts/
├── Rules/          ← 普通 C#，不碰 UnityEngine（這個習慣最重要）
│   ├── BigNumber.cs
│   ├── HitResolver.cs / TriggerQueue.cs
│   ├── RunState.cs / RewardPool.cs
│   └── Content/    PegDef.cs, BallDef.cs, RelicDef.cs（純資料類別）
├── Game/           ← MonoBehaviour：球、釘子、盤面、UI、輸入、特效
└── Editor/         ← 編輯器工具（盤面驗證器等）
```

**等到 M2/M3，你真的要跑平衡模擬時**，再在 `Rules/` 上按右鍵 → Create → Assembly Definition，並建一個 Console 專案引用它：

```
Rules/            Pinball.Rules.asmdef         ← 禁止引用 UnityEngine
Game/             Pinball.Game.asmdef          ← refs Rules + UnityEngine
Tools/BalanceSim/ Console 專案（refs Rules）   ← 10,000 場模擬，不開 Unity
```

**加 asmdef 的好處**（那時才有意義）：強制 `Rules/` 不准 `using UnityEngine`（不然「純 C#」只是口號，半年後一定會有人寫進去）；而且 Console 專案要能編譯，就必須純淨。

**現在不加的代價**：到 M3 想把規則從 MonoBehaviour 裡拔出來時，可能要花幾天。**延後付款，不是災難。**

### D5. 資料驅動內容 ＋ id 式存檔

- 內容（釘子／球／遺物／盤面）用 **ScriptableObject 當編輯器介面**，但 Core 只認純資料類別（`PegDef` 等），由 Game 層在啟動時把 SO 轉成 Core 資料。
- **存檔只存字串 id，永不存 ScriptableObject 參照或索引**。否則調一次內容順序，所有玩家存檔壞掉。
- `SaveData` 從第一版就帶 `saveVersion` 與遷移函式，即使現在只有 v1。

### D6. 計分管線順序必須寫死

大數字遊戲 90% 的平衡災難來自「乘法與加法順序不明確」。把順序寫進**一個** `HitResolver`，用程式碼固定，不允許資料改順序：

```
1. 基礎值        peg.BaseValue
2. 全域加法      + Σ flat
3. 加法乘區      × (1 + Σ percent)          ← 百分比互相相加，不是相乘
4. 獨立乘法      × Π independentMultiplier  ← 每個遺物各自相乘，最珍貴
5. 連擊/指數      × comboMultiplier          ← 本球內複利，大數字的引擎
6. 暴擊          × critMultiplier
7. 觸發佇列      進佇列再處理（不遞迴直呼）
```

## 4. BigNumber 設計

`mantissa (double) × 10^exponent (int)`，正規化為 `mantissa ∈ [1,10)`。所有運算 O(1)。

```csharp
namespace Pinball.Core.Numerics
{
    /// <summary>value = Mantissa * 10^Exponent，Mantissa ∈ [1,10) 或 0。</summary>
    [Serializable]
    public readonly struct BigNumber : IComparable<BigNumber>, IEquatable<BigNumber>
    {
        public readonly double Mantissa;
        public readonly int Exponent;

        public static readonly BigNumber Zero = default;
        public static readonly BigNumber One  = new BigNumber(1d, 0);

        public bool IsZero => Mantissa == 0d;

        public BigNumber(double mantissa, int exponent)
        {
            if (mantissa == 0d || double.IsNaN(mantissa) || double.IsInfinity(mantissa))
            { Mantissa = 0d; Exponent = 0; return; }

            int shift = (int)Math.Floor(Math.Log10(Math.Abs(mantissa)));
            Mantissa = mantissa / Pow10(shift);
            Exponent = exponent + shift;
            Normalize();
        }

        private BigNumber(double mantissa, int exponent, bool _)
        { Mantissa = mantissa; Exponent = exponent; Normalize(); }

        private void Normalize()
        {
            // 處理浮點誤差與溢位，不改變唯讀欄位的語意
            // （實作時用 local 變數算出結果後一次指派，或用 Unsafe 寫入；
            //   見下方 static 工廠方法版本，較單純）
        }
        // ...運算子略，重點如下
    }
}
```

**運算子語意（關鍵）：

```csharp
public static BigNumber operator +(BigNumber a, BigNumber b)
{
    if (a.IsZero) return b;
    if (b.IsZero) return a;
    if (a.Exponent < b.Exponent) (a, b) = (b, a);
    int d = a.Exponent - b.Exponent;
    if (d > 17) return a;                       // b 已被浮點精度吃掉
    return FromRaw(a.Mantissa + b.Mantissa * Pow10(-d), a.Exponent);
}

public static BigNumber operator *(BigNumber a, BigNumber b)
    => FromRaw(a.Mantissa * b.Mantissa, a.Exponent + b.Exponent);

public static BigNumber operator /(BigNumber a, BigNumber b)
    => b.IsZero ? Zero : FromRaw(a.Mantissa / b.Mantissa, a.Exponent - b.Exponent);
```

**必要配套：**
- `implicit operator BigNumber(int/long/double)` 與 `explicit operator double` —— 讓既有程式碼無痛遷移。
- `CompareTo`：先比 `IsZero`，再比 `Exponent`，再比 `Mantissa`。
- **`Exponent` 上限保護**（例如 clamp 在 ±1,000,000），避免極端 build 造成 `int` 溢位變成負數 → 分數變 0 的災難性 bug。
- `ToDisplayString()`：`K/M/B/T/Qa/Qi/Sx/Sp/Oc/No/Dc` → 超過門檻改用 `1.23e45`。
- **格式化不要在 hot path 做**：每幀每顆球都 `ToString()` 會產生大量 GC。UI 每幀只格式化一次總分（或每 3 幀）。

**測試必備清單**（EditMode，跑 1 秒內）：
`0 + 0`、`1e30 + 1`（應等於 1e30）、`1e300 * 1e300`（不得溢位）、`CompareTo` 對稱性、`Parse`/`ToDisplayString` 往返、極端指數 clamp。

## 5. 決定性 RNG

不用 `UnityEngine.Random`（全域狀態、無法分叉、無法存檔回復）。自己寫一個 struct：

```csharp
namespace Pinball.Core.Rng
{
    /// <summary>xorshift64*：小、快、可序列化（只有一個 ulong state）。</summary>
    public struct DeterministicRng
    {
        private ulong _state;

        public DeterministicRng(ulong seed)
            => _state = seed == 0UL ? 0x9E3779B97F4A7C15UL : seed;

        public ulong State { get => _state; set => _state = value; }   // 存檔用

        public uint NextUInt()
        {
            _state ^= _state >> 12;
            _state ^= _state << 25;
            _state ^= _state >> 27;
            return (uint)((_state * 0x2545F4914F6CDD1DUL) >> 32);
        }

        public float  Next01() => (NextUInt() >> 8) * (1f / 16777216f);
        public bool   Chance(float p) => Next01() < p;
        public int    Range(int minInclusive, int maxExclusive)
            => minInclusive + (int)(NextUInt() % (uint)(maxExclusive - minInclusive));
        public DeterministicRng Fork(ulong salt)
            => new DeterministicRng(SplitMix64(_state ^ (salt * 0x9E3779B97F4A7C15UL)));
    }
}
```

**分流（streams）設計** — 每個用途一條獨立流，互不干擾，這是可複現性的關鍵：

| 流 | 用途 | 為什麼要獨立 |
|---|---|---|
| `MapStream` | 地圖生成 | 玩家在商店多按一次不該改變地圖 |
| `RewardStream` | 獎勵三選一 | 同上 |
| `ShotStream` | 每發球的暴擊、掉落 | 可重播單一發球 |
| `CosmeticStream` | 粒子、音效變體 | **絕不能影響玩法判定** |

每發球的判定流：`shotRng = run.Rng.ShotStream.Fork(shotIndex)`；每次命中：`hitRng = shotRng.Fork(hitIndex)`。物理軌跡不同也無所謂，判定序列一致。

## 6. 計分與觸發（肉鴿引擎的核心）

```csharp
public readonly struct HitEvent
{
    public readonly int  BallId;
    public readonly int  PegId;
    public readonly int  HitIndexInShot;   // 本發球第幾次命中（連擊來源）
    public readonly float ImpactSpeed;     // 撞擊速度（可作為條件）
    public readonly float ImpactAngleDeg;  // 撞擊角度
    public readonly bool IsCritical;       // 由 hitRng 判定，不由物理決定
}

public sealed class HitResolver
{
    private readonly TriggerQueue _queue = new TriggerQueue();

    public BigNumber Resolve(in HitEvent hit, RunStats s, ref BigNumber boardScore)
    {
        var v = _content.Pegs[hit.PegId].BaseValue;
        v += s.FlatScoreBonus;

        // 加法乘區：百分比先相加再一次乘，避免「每件 +50% 相乘」爆走
        v *= 1d + s.PercentSum;

        // 獨立乘法：最稀有、最珍貴的成長來源
        for (int i = 0; i < s.IndependentMultipliers.Count; i++)
            v *= s.IndependentMultipliers[i];

        v *= ComboMultiplier(hit, s);          // 本球內指數複利
        if (hit.IsCritical) v *= s.CritMultiplier;

        boardScore += v;
        _queue.PushFromHit(hit, s);            // 觸發不遞迴直呼，避免堆疊爆掉
        DrainQueue(s, ref boardScore);
        return v;
    }

    // ★ 保險絲：遺物連鎖是大數字遊戲最常見的當機／無限迴圈來源
    private const int MaxStepsPerShot = 512;
    private const int MaxTriggerDepth = 16;
}
```

**觸發佇列一定要有預算上限。**「A 觸發 B，B 觸發 A」在 200 小時的專案裡一定會發生，而且通常發生在玩家 build 成形的爽點上——當掉最傷。做法：每發球最多處理 N 步，超過就靜默丟棄（或標記 `overflowed` 供除錯），並在開發版印警告。

**內容資料模型（觸發／條件／動作）**——用資料組出遺物，而不是每個遺物寫一個 class：

```csharp
public enum TriggerKind { OnHit, OnBounce, OnPegDestroyed, OnShotStart, OnShotEnd, OnBallLost, OnScoreGain }
public enum ActionKind  { AddFlat, AddPercent, AddIndependentMultiplier,
                          MultiplyCombo, SpawnBall, AddPeg, ApplyMark, GrantCurrency, HealPlayer }

[Serializable] public struct EffectDef
{
    public TriggerKind Trigger;
    public ConditionDef[] Conditions;   // HasTag("Bumper") / EveryNth(10) / SpeedAbove(8) / IsCritical
    public ActionDef[]    Actions;
    public int            MaxTriggersPerShot;   // 防爆保險，每件遺物各自設
}
```

好處：新增 40 件遺物＝填表，不寫程式；平衡調整＝改數字；也讓未來的「遺物稀有度／合成／升級」只是資料欄位。

## 7. 肉鴿層（Run 結構）

### 一局的形狀（建議）

```
選角/選起始球 → [ 節點地圖 ] → Boss → 下一層 → … → 第 8 層 Boss → 通關/失敗
                 ├ 戰鬥（盤面）   ├ 精英   ├ 商店   ├ 事件   ├ 寶箱   └ 營火（升級）
```

用 **線性樓層 + 節點分歧**（Slay the Spire 風），而不是開放地圖。理由：彈珠盤面的「關卡設計成本」很高，開放地圖只會讓玩家看到重複盤面。

### 盤面生成

**手做 chunk ＋ 種子化拼裝 ＋ 驗證器**。不要純程序生成——物理盤面的難度變異太大，純程序生成會產出「球必卡死」或「一發通關」的盤面。

```
Board = 3~5 個手工 chunk（入口/中段/出口）由 MapStream 選序組裝
驗證器（編輯器工具）：投放 200 次隨機球，檢查
  - 卡球率 < 1%
  - 得分分布標準差在可接受區間
  - 每次投球最終都能抵達出口
```

這個驗證器就是你的「關卡設計自動測試」，能省下大量手工試玩。

### 獎勵

- 三選一（依稀有度加權 + pity + 不重複規則），全走 `RewardStream`。
- 獎勵類型：遺物、球升級、釘子改造、資源、一次性消耗品。
- 稀有度權重隨樓層變化（越深越容易出高稀有度），公式放規則層，M3 可被模擬驗證。

## 8. 大數字經濟曲線

### 三種成長來源（缺一不可）

| 類型 | 例子 | 遊戲感 |
|---|---|---|
| 加法 | 每顆釘子 +5 分 | 前期有感，後期無感 |
| 乘法（加法乘區） | 所有得分 +30% | 中期主力 |
| **獨立乘法** | 每件遺物 ×1.5，各自相乘 | 後期爆走來源，最稀有 |
| **指數（本球內複利）** | 同一球每命中一次 ×1.15 | **大數字的靈魂** |

### 建議的 build 引擎原型（先做這 5 種，涵蓋大部分樂趣）

1. **連擊引擎**：單球內每命中 ×1.15 → 需要「讓球活更久」的配套（彈簧釘、低摩擦、減速、分裂）→ 自然形成 build 方向。
2. **暴擊引擎**：暴擊率可超過 100%，超出部分轉為暴擊倍率（經典且好懂）。
3. **標記引擎**：命中標記釘引爆連鎖，釘子之間互相觸發。
4. **轉換引擎**：金幣 → 分數、分數 → 球數、球數 → 倍率（跨資源轉換，讓資源不閒置）。
5. **盤面改造引擎**：把普通釘升級成炸彈釘／分數釘，或者自動加釘——**這是本作差異化最強的一條**。

### 平衡原則

- 關卡目標與敵人 HP 用**同一條曲線**成長（例如每層 ×3.5）。玩家平均每層成長要略高於 ×3.5（建議 ×3.8–4.5），才能持續有「變強」的爽感。
- **加法區要隨樓層縮放**，否則後期加法完全被乘法吃掉，相關遺物變成廢物。
- **乘法區要分級**（加法乘區 vs 獨立乘），否則「+50%」跟「×1.5」對玩家無法區分。
- **觸發次數上限**是數值上限，也是效能保險。
- **用 headless 模擬驗證，不要靠手感**：目標通關率 30–45%、平均在第 7–9 層結束。每次改遺物數值就重跑 10,000 場，看分布圖。

### 通膨的反制（後期內容）

- **Ascension / Stake 難度層**（Balatro 式）：通關後解鎖更高難度，附帶負面規則。
- **層數上限 + 無限模式**：正式局 8 層，通關後開無限樓層專供大數字玩家。
- **教學式數字呈現**：`1.23e45` 與 `1.23Dc` 切換，讓玩家自己選爽度。

## 9. 效能策略（大量球的關鍵）

這一節決定你的遊戲能不能做到「1000 顆球同時飛」。

| 項目 | 做法 |
|---|---|
| 設定 | `Physics2D.Simulation Mode = FixedUpdate`、Velocity Iterations 8+、用 Layer Matrix 關閉球對球碰撞（除非刻意要） |
| 球 | `Rigidbody2D` + `CircleCollider2D`、`collisionDetectionMode = Continuous`、**物件池**、`sleepMode = NeverSleep`（活動球） |
| 釘子 | 靜態 collider、不要 Rigidbody、依種類分 Layer |
| 飄字 | 物件池上限（例如 64）、**同一幀同一顆釘子的多次命中合併成一個數字** |
| 計分 UI | 每幀只讀一次聚合值，數字用 lerp 追上（視覺爽感＋省效能） |
| GC | hot path 不用 LINQ、不用 `foreach`（用 array + for）、不產生字串、`HitEvent` 用 struct 傳 `in` |
| 球數爆炸 | 活躍球超過門檻（例如 150）→ **統計模式**：把 K 顆球壓縮成 1 顆 × K 分，畫面只保留少量代表球。同類遊戲實務上都這樣處理 |

> 統計模式要**從架構上預留**：`BallController` 不應該是規則的唯一來源，而是「產生 HitEvent」的來源；當球被壓縮時，由 Core 用機率模型產生等價的 HitEvent 流。這也是三層架構的紅利。

## 14. 柏青哥定位的連鎖影響

選了柏青哥式，會連帶鬆動方案裡四個原本的預設。逐項說明並編號為 T1–T6 設計題（**現已全數定案**，見第 13 節）。

### 連鎖影響 1：「瞄準＋反彈預測」可能要退場

原本第 13 節建議 Peglin 式的瞄準與預測線。但真實柏青哥**不瞄準**——玩家只控制**發射力度**，力度決定球從盤面哪一側、什麼角度進入。這是更極簡也更道地的輸入：**一根力度條**。

- 好處：操作門檻極低、移植手把／手機容易、把玩家的注意力從「瞄準」移到別的地方。
- 風險：若盤面是固定的，玩家在投球時的參與感會趨近於零（只能看）。**這是 T1 選 (c) 之後最大的風險，必須靠第 15 節的設計補回。**

### 連鎖影響 2：build 軸的組成改變

原本假設「盤面構築」是主力 build 軸，但 T1 選 (c) 之後盤面是固定的，**盤面元件不再是獎勵**（它是關卡設計），build 軸回到遺物與球：

| 元素 | 角色 | 說明 |
|---|---|---|
| 遺物 | **主力 build 軸** | 但它們要能**改寫盤面規則**（轉化釘子、生成機關、改物理常數），不只是改數字 |
| 球 | **主力 build 軸** | 球的物理屬性（彈性／重量／半徑／磁力／分裂）＝ 同一張盤面玩出不同路線 |
| 盤面 | 關卡設計／謎題 | 固定但手工設計，每層有主題與解法；**不是**玩家可編輯的資源 |
| 釘子 | 盤面的一部分 | 可被遺物轉化，但不是獎勵選項 |

### 連鎖影響 3：大數字的「爆發結構」有現成範本

柏青哥真正的情緒曲線不是「穩定得分」，而是：

```
累積（球不斷落入一般落袋，期待升高）
  → 觸發（進入特定落袋／當選）
  → 爆發（大量球湧入，數字指數跳升）
  → 期待下一輪
```

**這正好就是大數字遊戲最需要的曲線**，而且是柏青哥的原生結構。建議把它做成顯式的遊戲機制（例：某些釘子累積「期待值」，滿了就進入 10 秒的「當選模式」，所有得分 ×50 並連發球）。這比「每層目標 ×3.5」的平鋪曲線有趣得多，也是第 8 節經濟曲線更好的載體。

### 連鎖影響 4：失敗條件需要重新發明

真實柏青哥沒有「輸」，只有「錢花完」。肉鴿一定要有明確的失敗。候選：

| 方案 | 說明 | 評價 |
|---|---|---|
| A. 球數耗盡未達標 | 每層給 N 顆球，達標才過關 | 最直覺，與現有 M0 設計一致 |
| B. 盤面 HP／防線被突破 | 有東西從下方漏出去就扣血，歸零即敗 | 提供壓力與即時張力，可與 A 並用 |
| C. 資源耗盡（賭本歸零） | 最貼近柏青哥，但對玩家偏抽象 | 適合作為第二層資源，不宜當唯一條件 |

> **最終定案（T4）**：不是「行動次數 vs 生命線」的雙軌，而是**單軌的 DPS 檢定**——每層在 N 回合內把敵人 HP 打到 0，否則本局結束。詳見 **15.5**。
> 這個定案比下面三個候選都好，因為它把「回合上限」「球數」「敵人 HP」統一成同一個資源，玩家只需要理解一個數字。

## 15. T1 定案 (c)：完全固定盤面 —— 具體設計草稿

### 15.0 這個選擇換到什麼、付出什麼

| 換到 | 付出 |
|---|---|
| **M1 範圍大幅縮小**：不需要盤面編輯器、不需要玩家可見的盤面分析器 UI | **「自己擺盤」的直覺賣點消失**，行銷與定位要換鉤子 |
| 關卡設計完全可控，平衡容易（每張盤面可手工調到「好玩」） | 盤面數量＝內容量，需要穩定的盤面產能 |
| 盤面可以有**身份**：漏斗層、迷宮層、雙塔層、Boss 機關層 | 投球當下玩家只剩一根力度條 → **參與感是唯一致命風險** |
| 球的物理屬性成為主要 build 軸，這條軸比 Ballionaire 少見 | 物理不確定性高，玩家容易覺得「是運氣不是技術」 |

**唯一要解決的核心問題：球落下時，玩家在做什麼？**
本節 15.1（力度）＋ 15.2（球）＋ **15.8（主動技能）** 就是這個問題的答案。若這三者做不出深度，(c) 就會變成「看動畫的放置遊戲」——那不如直接改回 (b)。

### 15.1 發射系統：力度是主要的即時輸入，且必須「可學習」

> 註：T3 定案後，即時輸入還包含**有限次數的主動技能**（見 15.8）。本節只講發射力度。

真實柏青哥的技術全在**力度控制**：球從右下沿右側軌道上升，力度決定它爬到多高、從哪一層切入盤面。這是可學習、有深度的技巧，不是隨機。

**設計：**

```
[ 發射軌道 ] 球由此出發 → 沿右側軌道上升 → 依力度決定脫離高度 → 從盤面左側切入
  力度 0–100%（按住蓄力、放開擊出）
```

- 力度**不是瞄準某一點**，而是「選擇從哪一層進場」。盤面被切成 5–6 個「進場層」，每一層對應完全不同的路徑與得分期望。
- 力度條上有**玩家自訂書籤刻度**（像高爾夫遊戲的擊球點）。玩家會自己歸納出「37% 走左漏斗、62% 直落中央」——**這個歸納過程就是遊戲的技巧成長曲線**，也是 (c) 唯一能提供的操作深度。
- **必須有教學盤面**：一張只有 3 個進場層、路徑清晰可見的盤面，專門教玩家「力度↔路線」的對應。這比任何文字教學都有效。
- 力度帶有 **±2% 隨機擾動**（由 `ShotStream` 決定）→ 保留賭感、避免變成純機械操作。擾動幅度是重要旋鈕：太大＝玩家覺得被騙，太小＝變成背答案。

**解決「物理不可預測」的 UX 護欄（必做，排 M1）：**
- **幽靈預覽**：每層開局可花費 1 顆球做「試投」，只看軌跡不計分。或者免費 3 次。
- **落點熱區顯示**：盤面底部以淡色顯示各進場層的歷史落點分布（本層內累積）。玩家看得見自己的力度選擇造成什麼結果。
- 沒有這兩者，(c) 一定失敗——玩家會覺得一切都是運氣。

**動態機關**（不給放置權，但讓盤面會動）：
旋轉桿、開合閘門、移動釘牆、風扇區、磁力區、傳送門。Boss 盤面的核心。這些讓固定盤面仍有「解法」可研究。

### 15.2 球的物理屬性：真正的主力 build 軸

玩家的長期成長主要來自**換球、升級球、混搭球**。同一張固定盤面，不同球完全是不同遊戲。

| 屬性 | 範圍 | 對玩法的意義 |
|---|---|---|
| **彈性** bounciness | 0.30 – 0.95 | 高彈＝亂跳（碰更多釘、分數高但隨機）；低彈＝走固定路線（可控、適合狙擊特定落袋） |
| **重量** mass | 0.5 / 1 / 3 | 影響被機關推動的程度、速度衰減、是否推得開閘門 |
| **半徑** | 0.08 / 0.12 / 0.18 | 小＝穿過窄縫但難觸發；大＝易碰撞但可能卡住 |
| **磁力** | −1 / 0 / +1 | 吸引或排斥特定顏色的釘子 → **主動控制路徑**，是唯一能「對抗物理隨機」的屬性 |
| **穿透** | 0 – 3 | 撞擊後穿過 N 顆釘不反彈 → 為「直線衝底」型盤面而生 |
| **分裂** | 0 / 2 / 3 | 撞擊 N 次後分裂成多顆 → 球數爆炸、當選模式的主要燃料 |
| **屬性附魔** | 火／冰／雷／毒 | 與釘子的標記系統互動，是遺物連鎖的介面 |

**球的稀有度與成長：**
- 球可以**升級**（等級提升屬性）與**改造**（附加詞條，如「+15% 對炸彈釘傷害」）。
- 玩家帶 **2–3 顆球**進層，每顆球每層可發射有限次數 → 「這顆球該用在哪一層」本身是決策。

> **這條軸的戰略價值**：它讓 (c) 依然有「構築」感，而且與 Peglin（固定球＋固定盤面＋遺物）和 Ballionaire（擺盤）都不同。**「配球」是本作可以主打的一句話。**

### 15.3 遺物如何「改寫盤面」——支柱三的最後防線

玩家不擺盤，但盤面必須在過程中**變得面目全非**，否則「構築改變盤面行為」這根支柱會倒。做法：遺物只做**執行期轉化**，不做放置。

| 類別 | 例子 | 效果 |
|---|---|---|
| **轉化** | 「每 15 次命中，隨機一顆普通釘變成炸彈釘」 | 盤面逐步異變，後期盤面完全不同 |
| **增殖** | 「擊破敵人釘時原地生成 2 顆小釘」 | 盤面越打越密，得分指數上升 |
| **連鎖** | 「命中 A 釘時，對最近的 B 釘發射一次虛擬命中」 | 觸發佇列的來源，要注意步數上限 |
| **改寫規則** | 「所有釘子 +1 分，但每顆釘只能被碰 3 次就熄滅」 | 改變盤面的**使用方式**，而非幾何 |
| **生成機關** | 「在盤面固定位置生成一座旋轉桿」 | 引入動態元素 |
| **改物理常數** | 「重力 ×1.2」「所有反彈 +0.1」 | 全域体感改變 |

**目標**：讓玩家在第 8 層回頭看，同一張固定盤面已經長得跟第 1 層完全不一樣。這是 (c) 能成立的關鍵補償設計。

### 15.4 爆發結構（當選模式）：本作的情緒高點

柏青哥的原生情緒曲線正是大數字遊戲需要的曲線，必須做成**顯式機制**：

```
球落入「啟動落袋」→ 期待值累積（可見計量條，有音效逐漸堆疊）
    → 期待值滿 → 【當選】→ 10 秒／N 顆球內：
         所有得分 ×50、發射不消耗球數、盤面機關全開、球自動分裂
    → 當選期間再次觸發當選 → 【連莊】，倍率複利（×50 → ×250 → …）
    → 連莊結束 → 一切歸零，玩家渴望下一次
```

- **連莊是本作的最高潮**，也是 build 的終極目標：玩家整局都在為「能不能連莊」做準備。
- 這就是第 8 節經濟曲線真正的載體——**指數成長發生在連莊裡，而不是平鋪在每一層**。這比「每層目標 ×3.5」健康得多，也更好平衡（爆發是脈衝式的，可控）。
- 需要**當選模式的節奏設計**：進入時的儀式感（畫面、音效、鏡頭）、期間的資訊密度（數字狂跳但不能看不清）、結束時的結算畫面（「本次當選獲得 X 分」）。

**✅ M0 範圍（已定案）：只做簡化版**

| 項目 | M0 簡化版 | M3 完整版 |
|---|---|---|
| 觸發 | 1 個啟動落袋 | 多個落袋＋不同期望值 |
| 持續 | 固定 8 秒 | 依 build 延長 |
| 倍率 | 固定 ×50，**不複利** | 連莊複利（×50 → ×250 → …） |
| 機關 | 不變 | 機關全開、球自動分裂 |
| 目的 | **只驗證「累積→爆發」的手感是否成立** | 完整的經濟曲線載體 |

理由：連莊複利牽動整個經濟曲線與平衡，在核心手感未驗證前做它，等於在沙地上蓋房子。M0 只要證明「期待值計量條填滿的那一刻很爽」就夠了。

### 15.5 失敗條件（T4 定案）：每層＝一次 DPS 檢定

| 元素 | 內容 |
|---|---|
| 敵人 | 每層一個敵人，HP 為 `BigNumber`，隨樓層曲線成長 |
| 回合上限 | 每層給 N 回合（起始 **8**） |
| 過關 | 在 N 回合內把敵人 HP 打到 0 |
| 失敗 | N 回合用完敵人仍存活 → 本局結束 |

**「一回合」的定義**：配合 T2（初始一次一顆球），**1 回合 ＝ 1 次投球**。這讓「回合上限」「球數」「DPS 檢定」統一成同一個資源——**玩家只需要理解一個數字**。這是這個設計最漂亮的地方。

**與當選模式的協同（本作的核心循環）：**

```
        投球累積分數 ──→ 分數轉傷害 ──→ 敵人 HP 下降
             ↑                                │
        落入啟動落袋                     HP 還剩很多、回合快用完
             ↑                                │
        期待值滿 ──→【當選】×50 爆發 ──→ 一波帶走
```

當選模式是 DPS 檢定的解答，DPS 檢定是玩家想開當選的動機。**這個循環自我驅動，不需要額外的外力推。**

**敵人設計：** 完整的敵人機制（軟護甲、適應裝甲、易傷疊層）與敵人位置（在盤面上／盤面外）見**第 18 節**。M0 只用「純 HP 木樁 ＋ 軟護甲」驗證數字循環與流派效率差。

**球的落袋要分級**（柏青哥的精髓，也是失敗壓力的來源）：

| 落袋 | 結果 |
|---|---|
| 普通落袋 | 少量分數 |
| 得分落袋 | 中量分數＋資源 |
| **啟動落袋** | 累積期待值（當選的門票） |
| **失誤落袋** | **本回合分數不轉換成傷害** → 白白浪費一個回合（這就是壓力來源） |
| **回收落袋** | **返還 1 回合**（不消耗）→ 稀有，是延長局的關鍵資源 |

### 15.6 因為 (c) 而修正的 M0 與里程碑

**M0 範圍縮小：**

- ❌ 不需要：盤面編輯器、玩家可見的盤面分析器 UI
- ✅ 需要：1 張**手工設計的固定盤面**＋右側發射軌道＋蓄力力度條（含書籤刻度）、球的 3 種屬性（彈性／重量／分裂）、8 件遺物（含 2 件「轉化盤面」類）、當選模式原型（1 個啟動落袋）、幽靈試投

**M0 驗收標準改變（重要）：**

> 舊：「連續玩 30 發不無聊」
> 新：「**同一張盤面投 30 次，玩家是否自己歸納出『力度 ↔ 路線』的對應，並且開始有偏好？**」

後者是 (c) 唯一的核心手感驗證。如果 30 次之後玩家仍覺得「每次都是隨機」，那 (c) 必須改回 (b)，或改用 15.1 的熱區顯示／磁力球來補救。**這個驗證要在 M0 就用灰盒做完，不要等到 M2。**

**M1 追加項：** 幽靈試投與落點熱區顯示（見 15.1）——這是 (c) 的必要護欄，不可延後。

### 15.7 (c) 的定位重寫（行銷鉤子）

既然「自己擺盤」不能用了，對外的一句話要換：

> ~~「打造你自己的柏青哥盤面」~~
> **「同一座machine，用不同的球打出完全不同的結局」** —— 主打**配球 × 遺物改寫盤面 × 連莊爆發**。

差異化矩陣：

| 遊戲 | 操作 | 構築 | 本作差異 |
|---|---|---|---|
| Peglin | 瞄準反彈 | 遺物＋球 | 本作無瞄準、有連莊爆發 |
| Ballionaire | 擺盤 | 盤面元件 | 本作盤面固定、主打配球 |
| **本作** | **力度＋時機＋有限主動技能** | **球＋改寫盤面的遺物** | **連莊指數爆發＋配球策略** |

### 15.8 主動技能（T3 定案後的具體設計）

**設計原則（三條，違反任何一條就不做）：**

1. **技能必須是有限資源**（次數不跨層累積），否則玩家會無腦連放，操作深度歸零。
2. **技能必須與盤面互動**（改變球的軌跡），不能只是「+50 分」——加數字請交給遺物。
3. **技能必須能被遺物改造**（+次數、強化效果、技能連動），這樣技能本身也是 build 軸。

**M0 實作這 3 個（依重要性排序）：**

#### ① 拍打／機台推擠（Nudge）— 每層 3 次 ⭐ 最重要

- **效果**：對所有正在下落的球施加一個水平推力（例：+2.0 m/s，方向可選左／右）。
- **用途**：唯一能**在中途介入**的手段。救回即將落入失誤落袋的球、把球推過窄縫、把球踢向啟動落袋。
- **為什麼最重要**：它直接解決 (c) 的參與感風險。有了拍打，球落下時玩家不再只是觀眾。
- **真實感**：這是真實彈珠台的經典機制，附帶 **Tilt 機制**——連續拍打超過閾值就進入 5 秒逞罰（不能拍打）。Tilt 可以留到 M3，但架構要預留（`NudgeBudget` ＋ `TiltState` 放 Core）。
- **回饋**：機台畫面震動、音效、球被推的即時視覺。

#### ② 磁力脈衝（Magnet Pulse）— 每層 2 次

- **效果**：3 秒內，指定半徑 R 內的所有球被吸引向玩家指定的釘子。
- **用途**：把球導向啟動落袋或倍率釘 → **直接服務於當選爆發**。
- **為什麼好**：與「磁力球」屬性同源，兩者可互相強化 → 一條清晰的 build 軸（磁力 build）。
- **互動**：與磁力球疊加時效果加倍，但磁力球的高磁力會讓球難以離開 → 天然取捨。

#### ③ 集中／慢動作（Focus）— 每層 1 次

- **效果**：3 秒內 `timeScale = 0.3`。
- **用途**：操作精度的放大器，與 ①② 組合使用（慢動作中精準拍打）。
- **為什麼好**：實作成本極低（一個 `timeScale` 插值），但提供**高潮時刻的操作感**。這是「我做了判斷」的來源。
- **注意**：物理用 `FixedUpdate`，慢動作不影響物理正確性；但音效需要 pitch 配合，否則會很怪。

**M3 再擴充（先不做）：** 追加投球（立即再發一顆、不消耗球數）、時光回溯（重放本球）、技能連動（拍打觸發磁力）。

**「時機」從哪來？** 不需要額外 UI——來自**盤面機關**：旋轉桿、開合閘門、移動釘牆在動，放開力度的時機決定球能否穿過開著的閘門。這是免費的技術深度，且讓每張盤面有自己的節奏。

**技能經濟：**

| 規則 | 數值（起始） | 說明 |
|---|---|---|
| 每層初始次數 | 拍打 3／磁力 2／集中 1 | 依難度層與遺物變化 |
| 跨層累積 | **不累積**（重置為初始值） | 逼玩家當層用完，避免囤積到 Boss |
| 遺物改造 | +1 次數／效果 ×1.5／技能連動 | 技能成為 build 軸 |
| 顯示 | 技能列在盤面下方，含剩餘次數 | 玩家必須隨時知道資源 |


### 15.9 單發節奏：球數是「肉鴿解鎖項」（T2 定案）

**基礎行為：一次一顆球。** 但「同時能投幾顆」「發射間隔」「是否自動連發」**全部是肉鴿獎勵**。

| 解鎖項 | 效果 | 稀有度 |
|---|---|---|
| 雙球／三球 | 同時投出多顆，角度略分岔 | 中 |
| 快速裝填 | 發射間隔 −40% | 中 |
| 分裂球 | 球撞擊 N 次後分裂（球的屬性，見 15.2） | 中 |
| 自動連發 | 球落地後 0.3 秒自動發射下一顆 | 高 |
| 追加投球 | 主動技能：立即再發一顆，不消耗回合（見 15.8） | 高 |

**為什麼這比「一開始就多球」好（也是這個答案比我原推薦好的地方）：**

1. **學習環境乾淨** —— 前 1–2 層只有一顆球，玩家能清楚觀察「力度 → 進場層 → 路徑 → 落袋」的因果鏈。多球會讓因果模糊，玩家永遠學不會 15.1 的技巧。
2. **權力曲線看得見** —— 第 1 層 1 顆球 → 第 8 層同時 20 顆球在盤面上。**這個畫面本身就是最好的預告片，也是最強的成長回饋。**
3. **構築有明確階段感** —— 早期（1 顆）研究路徑、中期（3–5 顆）疊加得分、後期（20+ 顆）看數字爆炸。
4. **效能壓力漸進** —— 球數上限由玩家自己的獎勵選擇決定，等於玩家自己決定何時把遊戲推進到需要「統計模式」（第 9 節）的階段。效能問題因此是可預期、可規劃的。

## 16. 攻擊模型：分數 → 傷害（T6 定案）

### 16.0 這解決了什麼問題

大數字遊戲最根本的難題是：**如果數字只是分數，玩家為什麼要在乎它？**

把分數接到敵人 HP 上，一次解決三件事：

1. **數字有了後果** —— 數字不只是排行榜，它決定你能不能活過這一層。
2. **盤面有了用途** —— 盤面是「得分引擎」，也就是你的武器。15.2 的配球、15.3 的遺物改造盤面，全部直接影響戰力。
3. **肉鴿與大數字接上了** —— 遺物同時給你「更多分數」與「更高轉換率」，兩者都是 build 軸。

### 16.1 核心公式

```
盤面命中：    分數（BigNumber，來自盤面）  →  存入充能條
充能條滿格：  自動開火 →  本次能量 × 轉換率（double，build 軸）  =  傷害
              敵人HP  -=  傷害
```

> **時序以第 17 節為準**：不是「球落地就自動轉換」，也不是「玩家手動釋放」，而是「**充能條滿格就自動開火**」。這個改動是本方案最關鍵的一步，理由見 17.3、17.4。

- **本次能量**：充能條從上次開火累積到現在的分數總和（= 充能上限，或含溢出）。
- **轉換率**：起始 **10%**，且**隨攻擊大小成長**（17.4.1）。是主要 build 軸之一。
- **充能上限**：決定攻擊頻率，**是最重要的 build 軸**（17.4）。
- **敵人 HP**：`BigNumber`，與玩家成長曲線匹配。

### 16.2 兩條獨立的指數軸（大數字的正當來源）

| 軸 | 來源 | 成長型態 |
|---|---|---|
| **軸 A：盤面分數** | 釘子品質、連擊、當選模式、配球 | 單球內複利 → 指數 |
| **軸 B：轉換率** | 遺物、球升級、商店 | 加法＋乘法 → 指數 |
| **傷害 ＝ A × B** | — | **兩條指數軸相乘 → 這才是大數字** |

這比「分數直接等於傷害」好，因為它給了玩家**兩個獨立且都有效的成長方向**。當軸 A 遇到瓶頸（盤面就這麼多釘子），玩家會轉向軸 B；反之亦然。這正是肉鴿需要的深度。

> ⚠️ **這也是本方案最大的平衡風險**：A 與 B 都指數成長，敵人 HP 必須以接近「雙指數」的速度成長，否則第 6 層之後遊戲就結束了。**這是 headless 模擬（第 2 節）最重要的工作，也是它存在的理由。**
>
> **緩解**：17.4.1 的「轉換率隨攻擊大小成長」把軸 B 綁在單次攻擊的體量上（而非獨立成長），並**同時扮演平衡兩個流派的砝碼**。整體因此回到**單一主軸的複合指數**，比兩條完全獨立的指數好平衡得多。**先做 17.4.1，不要急著讓軸 B 有獨立的指數成長來源。**

### 16.3 四個變體（✅ 採用 #2）

| # | 模型 | 說明 | 產生的決策 |
|---|---|---|---|
| 1 | 即時轉換 | 每次命中立刻把分數轉成傷害 | 無 → 大數字看不見、沒有節奏 |
| **2** | **充能條 ＋ 閾值自動開火**（✅ 採用） | 分數充能，**滿格自動開火**；**充能上限本身是 build 軸** | **「我要更多次，還是更大一發」**（發生在構築層） |
| 3 | 手動釋放 | 玩家決定何時釋放 | ⛔ **已淘汰**：決策會退化，見 17.3 |
| 4 | 分數雙用途 | 分數同時轉傷害與資源 | 資源分配的取捨（M2 再評估） |

**#2 完勝 #3 的原因**（詳見 17.3）：自動開火把「結算時機」這個會被玩壞的決策移除，並把玩家能動性還給「投球力度、主動技能、構築選擇」這三個真正該由玩家決定的地方；同時**充能上限變成一個可讀性極高的 build 軸**，天生產生兩個互斥流派。

### 16.4 與其他系統的接點

| 系統 | 如何接上 |
|---|---|
| 當選模式（15.4） | 當選期間分數 ×50 → 傷害 ×50。**當選 ＝ 爆發窗口** |
| 配球（15.2） | 不同球產生不同分數曲線 → 不同 DPS 特性 |
| 遺物（15.3） | 同時作用於軸 A（更多分／更會連擊）與軸 B（更高轉換率） |
| 主動技能（15.8） | 磁力脈衝把球導向啟動落袋 → 為了開當選 → 為了傷害 |
| 失敗條件（15.5） | 回合上限 ＝ DPS 檢定 → 給「追求爆發」一個明確動機 |

**這張表就是本作的完整核心循環：所有系統都收斂到同一個目標上。** 這是設計健康的訊號——如果某個系統接不上這張表，它大概就不該存在。

### 16.5 呈現上的注意事項

- **畫面上同時有兩個數字，但角色不同**：分數是**持續跳動的引擎轉速表**，傷害是**落地時的一次重擊數字**。用大小、位置、動畫明確區分，不要讓玩家混淆。
- **傷害數字要比分數更誇張**（放大、震屏、短暫停頓）——它是「結果」，是爽感的高潮。
- 轉換率必須是 `double` 而**不能是 `BigNumber`**，否則「10%」這種小數無法表示（見第 3 節 D3 的型別分工）。

## 17. 基礎玩法與成長空間（低保底核心循環）

> 本節解決設計上最關鍵的一個問題：**沒有肉鴿構築時，玩法是什麼？**
> 結論：**機制從第一秒就完整，數值從第一秒就微小。** 構築不引入新機制，只放大既有機制。

### 17.0 問題診斷：混淆了「機制」與「規模」

常見的兩個錯誤方向，都是試圖用**解鎖**來製造成長空間：

| 錯誤方向 | 內容 | 為什麼錯 |
|---|---|---|
| 甲 | 基礎是「一球一傷害」；分數→傷害只是**其中一個流派** | 基礎玩法裡沒有分數的位置 → 大數字爽感**失去種子**，後期很難長成主軸 |
| 乙 | 分數與傷害是基石，但**前期分數沒用**，拿到強化才有用 | 前三層是**死時間**（玩家累積一個不生效的資源）；且違背直覺——**如果分數沒用，UI 為什麼要顯示它？** 介面在說謊 |

**正確做法**：轉換從第一天就生效，只是**很弱**。構築是「放大」而非「解鎖」。

> **「分數很弱」和「分數沒用」之間，差了一個完整的遊戲。**
> 前者是 Balatro 的第 1 回合（籌碼 × 倍率，結構完整、數值極小）；後者是三層樓的空轉。

**判斷標準（一句話）**：把第 1 層單獨抽出來，**它是不是一個完整的小遊戲？** 如果是，基礎玩法就對了。

### 17.1 核心原則

> **機制要完整，數值要微小。**
> 基礎玩法提供「完整的機制形狀 ＋ 極小的數值」；肉鴿構築不引入新機制，只提供**放大既有機制的槓桿**。

Balatro：沒有小丑牌時，打一副對子照樣是 `籌碼 × 倍率 = 分數`，結構完全一樣，只是打出 200 分而不是 200 萬分。小丑牌不是「解鎖乘法」，是「把乘法變大」。
Slay the Spire：沒有遺物時，出牌、格擋、攻擊的循環照樣成立。
**本作也要一樣。**

### 17.2 基礎玩法（第 1 層，零構築，玩家的前 3 分鐘）

```
拉力度條 → 放開 → 球沿軌道上升（懸念）→ 切入盤面開始彈跳
    ↓
每碰一顆釘子 → +1 分 → 存入【充能條】
    ↓
充能條是持續長大的數字：1 → 6 → 15 → 34 → 71 …
    ↓
⚡ 充能條滿 → 自動開火！→ 本次能量 × 轉換率(10%) = 傷害 → 敵人 HP 下降 → 充能條歸零
    ↓
球還在彈跳 → 繼續充能 → 再次開火 …（一顆球可以觸發多次）
    ↓
球落袋 → 投下一顆（1 回合 ＝ 1 投球）
```

**兩個爽點在第 1 層就都存在**，只是規模微小：
- **爽點 A**：充能條持續長大（1 → 71）
- **爽點 B**：充滿的瞬間自動開火，數字炸出來，充能條歸零重來

**而且爽點 B 是週期性反覆出現的**——因為攻擊可以在球還在彈跳時發生，一顆球可能開火好幾次。這比「每回合結算一次」的節奏感強得多，也讓「球活更久」的價值立刻看得見。

**「完美肉鴿構築」不是「終於解鎖了轉換」，而是充能上限被壓到極低、轉換率漲到 500%——同一顆球開火 8 次，每次都是核彈。** 同樣的機制，完全不同量級。

### 17.3 為什麼是「充能條 ＋ 閾值自動開火」（取代手動釋放）

| 問題 | 手動釋放（舊設計） | 閾值自動（定案） |
|---|---|---|
| 「存 vs 放」的決策 | **會退化**：轉換率單調遞增 →「永遠存到底」是唯一解 → 決策是假的，要靠補丁勉強救 | **這個問題不存在**，閾值自己決定，不需要任何補丁 |
| Build 軸的**可讀性** | 「轉換率 +50%」——抽象 | **「充能上限 100 → 20」——玩家一秒就懂：攻擊變 5 倍頻繁** |
| 產生的**流派數量** | 只有一條數值軸 | **天然產生兩個互相排斥的流派**（高頻 vs 大傷），逼出 build 身份 |
| **道地程度** | 真柏青哥沒有「釋放」按鈕 | **真柏青哥就是落袋自動派彩** → 更道地 |
| 玩家**能動性** | 由釋放按鈕提供 | 由 15.8 的主動技能提供 |

**最後一項是關鍵。** 舊設計讓「結算」承擔了「操作能動性」，但那不是結算的工作，而且做得不好（決策會退化）。自動化之後，**玩家的能動性集中在三個真正該由玩家決定的地方：投球的力度、主動技能的時機、構築的選擇**。

> 這也讓 **T8（等待的成本）整條作廢**——不再需要「敵人每回合壓力」來救「存 vs 放」，因為已經沒有「存」這個決策了。（敵人是否反擊仍是獨立的難度設計問題，見 15.5，但不再是為了修補能量機制。）

### 17.4 ⭐ 充能上限 ＝ build 軸：兩個流派

**充能上限不是一個固定常數，它是最重要的 build 軸之一。**

| | **低上限流派（高頻）** | **高上限流派（大傷）** |
|---|---|---|
| 充能上限 | 低 | 高 |
| 攻擊頻率 | 極高，一顆球可能開火 8+ 次 | 極低，可能每 5 顆球才開火一次 |
| 單次傷害 | 小 | 巨大 |
| 主要成長來源 | **每次攻擊都觸發的遺物效果**（見 17.4.1） | **轉換率隨攻擊大小成長**（見 17.4.1） |
| 對群體小怪 | 極強 | 溢傷浪費嚴重 |
| 對單體高 HP Boss | 無力（單發太癢） | 極強 |
| 當選模式（15.4 ×50） | **極強**（8 秒內狂開火） | 弱（8 秒內只開火 1–2 次） |
| 核心台詞 | **「我要更多次」** | **「我要更大一發」** |

**這兩個流派天然互斥**（上限只有一個數字，不能同時低又高），所以玩家的 build 身份被迫明確——這正是肉鴿最需要的東西。而且兩者的爽感**質地不同**：高頻流是「連續不斷的噠噠噠」，大傷流是「等待後的一擊必殺」。同一個基礎機制供養兩種完全不同的情緒，這是很高的設計效率。

### 17.4.1 ⭐ 兩個流派各自靠什麼成立（平衡的關鍵）

這個設計能不能成立，全看這裡：**如果沒有補償，低上限一定碾壓高上限**——因為同樣的能量，切越多次就觸發越多遺物、溢傷越少。

| 流派 | 靠什麼變強 | 機制 |
|---|---|---|
| **高上限（大傷）** | **轉換率隨攻擊大小成長** | `轉換率 = 基礎 × (1 + log10(本次攻擊能量) × k)` → **大攻擊的每一點能量更值錢**。一發 6,500 能量的轉換率可能是 200 能量的 3 倍 |
| **低上限（高頻）** | **攻擊次數本身就是資源** | 「每造成一次攻擊，全域傷害 +2%」「每次攻擊有 30% 機率加一個標記」→ 觸發型遺物把頻率換成戰力 |
| 兩者共同 | 暴擊 | 高頻＝更多暴擊判定次數（適合「暴擊率溢出轉暴傷」的 build）；大傷＝單發暴擊倍率更可觀 |
| 情境差異 | 敵人組成 | 群體小怪 favor 高頻；單體 Boss favor 大傷 |

> **原 17.4 的機制在這裡找到了正確的位置。** 我先前把它當成「讓玩家願意存」的動機，結果導致退化（T8）；現在它是**平衡兩個流派的砝碼**——讓「大上限」在效率上追得上「多段」。**同一個機制，換了工作就從 bug 變成 feature。**

### 17.4.2 溢能與溢傷的處理

| 情況 | 建議 | 理由 |
|---|---|---|
| **溢能**（單次賺的分數超過上限） | **保留溢出值並連續開火**。例：上限 20、一次賺 50 → 開火 2 次，剩 10 | 「一顆球賺很多」永遠是好事，符合第 8 節的爽感。**需注意第 6 節的觸發步數上限**（防無限連鎖） |
| **溢傷**（傷害超過敵人剩餘 HP） | **完全浪費** | 讓「剛好夠」成為技巧，也自然讓大傷流在打小怪時吃虧 → 強化兩個流派的取捨 |
| **上限被遺物降低時** | **立即連續開火**到低於新上限 | 「拿到遺物瞬間的爆發」很爽，保留。同樣受步數上限保護 |

### 17.4.3 ⚠️ 充能上限必須與「單球平均分數」同曲線成長

**這是實作上最容易踩的坑。**

若上限固定不變：第 1 層單球賺 5 分、上限 5 → 每顆球開火 1 次（很好）。但第 8 層單球賺 1,300 分、上限還是 5 → **一顆球開火 260 次**——節奏失控、效能爆炸、爽感變成噪音。

**解法**：`充能上限 = f(樓層)`，與單球平均分數走同一條曲線，讓「開火次數」保持在合理區間。

**而且要用「每顆球開火幾次」當玩家的顯示單位**，而不是顯示原始數值：

| 玩家看到的 | 意義 |
|---|---|
| 「每顆球約攻擊 **1** 次」 | 基礎值（第 1 層） |
| 「每顆球約攻擊 **8** 次」 | 高頻流成型 |
| 「每 **5** 顆球攻擊 1 次」 | 大傷流成型 |

這樣 build 軸的意義**極度可讀**——玩家不需要理解數字，只需要理解「我要每顆球打 8 次」還是「我要每 5 顆球打一發核彈」。**這比「轉換率 +50%」清楚一百倍，也是這個設計最大的優點。**

### 17.5 肉鴿構築放大的四個槓桿（＝成長空間）

| 槓桿 | 基礎值 | 構築後 | 玩家感受 |
|---|---|---|---|
| **軸 A：充能速度** | 1 分／釘 | 連擊複利 ×1.15ⁿ、倍率釘、低摩擦讓球活更久 | 充能條漲得越來越快 |
| **軸 B：轉換率** | 10% | 500%＋隨攻擊大小成長（17.4.1） | 同一發打得更痛 |
| **軸 C：充能上限** ⭐ | 每顆球開火 1 次 | 「每顆球 8 次」(高頻) 或「每 5 顆球 1 次」(大傷) | **決定攻擊的頻率與體量＝決定流派** |
| **軸 D：攻擊形態** | 單體一擊 | 多段打擊／擴散／持續傷害／全體 | **同一發能量，換一種打法** |

**軸 C 是第 17 節最重要的補充**（也是使用者提出的設計）：它是唯一一個**能讓玩家選擇「爽感質地」**的槓桿——高頻流是連續不斷的噠噠噠，大傷流是等待後的一擊必殺。

**軸 D 是「分數換成攻擊方式」的實現**，比單純換傷害更好——它讓「開火」本身成為 build 的一部分。

### 17.6 成長空間有多大：具體數字對照

| | 第 1 層（零構築） | 第 8 層 **高頻流** | 第 8 層 **大傷流** |
|---|---|---|---|
| 單球命中次數 | 約 5 次 | 約 40 次（彈簧釘＋低摩擦） | 約 40 次 |
| 連擊複利 | 無 | ×1.15⁴⁰ ≈ **×267** | ×1.15⁴⁰ ≈ **×267** |
| 單球分數 | 約 5 | 約 1,300 | 約 1,300 |
| **充能上限** | 5 | **200** | **6,500** |
| **每顆球開火次數** | **1** | **約 6.5** | **約 0.2** |
| 本次攻擊轉換率 | 10% | 12% | 20%（17.4.1 補償） |
| 單次傷害 | 0.5 | 約 24 | 約 1,300 |
| **單球總傷害** | **0.5** | **約 156** | **約 260** |
| 敵人 HP | 4 | 約 1,000 | 約 1,000 |

**兩個流派的 DPS 落在同一量級，但節奏完全不同**——這正是設計目標。高頻流每顆球開火 6 次以上（觸發型遺物吃滿）；大傷流每 5 顆球才開火一次，但一發就是 1,300。

**形狀完全一樣，規模差數百倍到數千倍。** 成長空間不是靠「解鎖新機制」擠出來的，是靠同一個機制被構築放大出來的。

（以上只是示範量級，實際曲線要用第 2 節的 headless 模擬驗證到第 15 層，並確認兩個流派的 DPS 長期維持在同一量級。）

### 17.7 基礎玩法的趣味性來自哪裡（第 1 層就必須有的五件事）

1. **物理的觀賞性與不確定性** —— 每次彈跳路徑都不同
2. **力度 → 路線的可學習性**（15.1）—— 技術成長曲線
3. **充能條持續跳動，並週期性地滿格開火** —— 微型的大數字爽感，而且**有節奏**（不是每回合一次的呆板結算）
4. **「這顆球能不能撐更久」的懸念** —— 球在盤面上越久＝充能越多次＝開火越多，價值立刻看得見
5. **主動技能的介入感**（15.8）—— 拍打救球

**這五件事全部不需要任何遺物就成立。** 這就是「基礎玩法有趣」的定義。

### 17.8 檢驗清單（M0 用）

| # | 檢驗 | 通過標準 |
|---|---|---|
| 1 | 第 1 層單獨玩，是否是一個完整的小遊戲？ | 機制完整（賺分 → 充能 → 自動開火 → 傷害 → 打倒），只是數字小 |
| 2 | 玩家是否能**立刻感受**到「充能上限」的差別？ | 調整上限後，玩家應能馬上說出「攻擊變頻繁了」或「變大發了」——**這是軸 C 成立與否的試金石** |
| 3 | **兩個流派的 DPS 是否在同一量級？**（17.4.1） | 若高頻流碾壓 → 加強大傷補償；若大傷流碾壓 → 反之。**用 headless 模擬驗證，不要靠手感** |
| 4 | 拿掉所有遺物，還想不想再玩一局？ | 若不想 → 基礎玩法有問題，**不要靠加內容掩蓋** |
| 5 | 玩家能否說出「構築讓我做的事變強了」而不是「構築讓我終於能做某件事」？ | 前者正確，後者是「解鎖式設計」的徵兆 |

## 18. 敵人設計：流派對策 與 敵人位置（T10、T11）

> 第 17 節讓「充能上限」成為最重要的 build 軸。但**如果沒有東西讓它產生情境差異，玩家只會算出哪個上限的 DPS 最高，然後永遠選它——build 軸就死了。**
> 本節的敵人機制，就是讓充能上限從「純 DPS 計算」變成「情境選擇」的東西。

### 18.1 兩種怪物是「讓 build 軸活起來」的機制，不只是平衡工具

| 怪物類型 | 利好流派 | 玩家學到的事 |
|---|---|---|
| 高防禦型 | **高上限（大傷）** | 「我的單發太癢，得存大一點」 |
| 連擊型 | **低上限（高頻）** | 「我要一直打，不能讓易傷斷掉」 |

**沒有這兩種怪物，充能上限就只是一個數字比較問題。有它們，同一個上限在不同房間有不同價值——這才是肉鴿。**

### 18.2 ⚠️ 硬護甲門檻在指數成長的遊戲裡會壞掉

若規則為「傷害 < 護甲 → 0 傷害」，這是一道**二元門檻**：

- 玩家會在拿到某個升級的**瞬間**從「完全打不動」跳到「直接輾過」，中間沒有過渡帶（指數成長讓這件事又快又突兀）
- **更嚴重：「完美構築可以一定程度強打」在硬門檻下根本做不到**——低於門檻就是 0，沒有「一定程度」

**修正：護甲用減免，但設下限。**

```
實際傷害 = max(傷害 × 護甲減免, 傷害 × 0.10)      // 最少造成 10%
```

低頻流打高防禦怪效率剩 10%——很慘但不絕望；**完美構築的低頻流真的能靠這 10% 硬推過去。**
> **這個下限是必需的，不是可選的**——它是 18.1「完美構築可以一定程度強打」能否成立的唯一保證。

### 18.3 易傷要寫成「疊層 ＋ 短時效 ＋ 清空」

單純的「受擊後易傷」太弱（只有第一次吃不到，之後全受益）。寫成疊層才是真正的頻率檢查：

> 每次受到傷害疊 1 層易傷（每層 +5% 受傷），持續 **2 秒**；2 秒內沒有再受傷則**全部清空**。

- 高頻流：疊到 10 層 = **+50%**
- 大傷流：永遠只疊到 1 層

**機制自我解釋：「連續命中才有回報」。**

### 18.4 ⭐ 建議追加：適應裝甲（比硬護甲更好的反高頻機制）

> 敵人每受到一次傷害，後續受到的傷害**遞減 15%**。

- 低頻大傷完全不受影響
- 高頻流第 10 次攻擊只剩 **23%** 效果

**為什麼比硬護甲好**：它是**連續的、沒有死局**，不會出現「打不動」的狀態；而且它與易傷是對稱的一體兩面（一個獎勵頻率、一個懲罰頻率）。

### 18.5 敵人機制總表

| 機制 | 利好 | 類型 | 風險 |
|---|---|---|---|
| 硬護甲門檻 | 高上限 | 數值檢查 | ⚠️ 指數成長瞬間跨過 → 從不可能變輾壓 |
| **軟護甲（10% 下限）** ⭐ | 高上限 | 數值檢查 | 安全，且實現「可強打」 |
| **適應裝甲（受擊遞減）** ⭐ | 高上限 | 機制對策 | 需明確重設條件 |
| **易傷疊層** ⭐ | 低上限 | 機制對策 | 好，自我解釋 |
| 單次傷害上限（每擊最多 HP 的 X%） | 低上限 | 機制對策 | 太硬會讓大傷流報廢 |
| 群體小怪（多目標） | 低上限 | 情境 | 大傷流溢傷浪費嚴重 |
| 單體高 HP | 高上限 | 情境 | 高頻流單發太癢 |

### 18.6 ⚠️ 房間選擇的前提：效率差 2–3 倍，不是「打不過」

若怪物硬性區分「高頻流才能打」與「大傷流才能打」，得到的**不是構築選擇，而是路線選擇**——玩家會被迫鎖死在單一流派，因為跨流派的路會被堵死。

**正確目標**：每個怪物都「打得過」，但對不同流派的**效率差 2–3 倍**。差距足以讓選擇有意義，但不至於卡死。

**必要條件**：**地圖必須預先顯示敵人類型**，否則這不是決策，是盲賭。

### 18.7 敵人位置（T11）：三個方案

| | 方案 A：在盤面上 | 方案 B：盤面外 | **方案 C（推薦）** |
|---|---|---|---|
| 物理連結 | ✅ 強 | ❌ 斷裂 | ✅ 強 |
| 盤面幾何是否改變 | ❌ **會變** | ✅ 不變 | ✅ **不變** |
| 15.1 力度↔路線可學習性 | ❌ **被摧毀** | ✅ 完整 | ✅ **完整** |
| 架構純淨度 | 中 | ✅ 高 | ✅ 高 |
| 實作難度 | 高 | 低 | 中 |
| 視覺爽感 | 高 | 低 | 高 |

#### ⚠️ 方案 A 的致命問題：它摧毀 15.1

整個 (c) 定案的技術根基是「**力度 ↔ 路線的可學習性**」（15.1）——玩家歸納出「37% 走左漏斗」並產生偏好。這是 (c) 唯一的技巧成長曲線，也是 M0 第一條驗收標準。

但若敵人會被打死、collider 消失，**盤面幾何就在同一層內改變了**：玩家剛學會的路徑突然通了、球路突然變了。**他學到的對應關係在戰鬥中失效。** 這不是小問題，是把 (c) 的地基抽掉。

#### ✅ 方案 C：敵人在盤面上，但碰撞幾何永不改變

- 敵人是一顆**大型靜態 collider**，放在盤面上（位置是關卡設計的一部分）
- 球撞到它 → **給大量分數，不給直接傷害**
- 充能滿 → 開火 → 扣敵人 HP
- HP 歸零 → 視覺上**碎裂成瓦礫**，但 collider 保留（或換成同形狀的瓦礫 collider）
- M0 實作時可直接讓敵人 collider 全程不消失，視覺替換即可

**關鍵細節：球撞敵人為什麼給「大分數」而不是「直接傷害」？**

因為這樣架構才是乾淨的：**球永遠只做一件事——賺分數；傷害永遠只來自開火。**（T6／T7 的身份不被稀釋。）

但感受上玩家仍然在「打敵人」：撞擊有火花、敵人會晃動，而且**撞敵人充能特別快 → 開火特別頻繁**。所以球打敵人是**間接但立即地**造成傷害。**物理連結與架構純淨，兩者都拿到了。**

**架構上更漂亮的是**：**敵人 ＝ 一顆「高價值釘子」＋ 一個 Core 層的 HP 值。**
- 釘子部分完全是盤面（固定、物理、由 Game 層管）
- HP 部分完全是規則層（`BigNumber`、由 Core 管）
- **Core 永遠不需要知道敵人的座標。**

#### 🎯 定案建議：**C 為預設，A 留給 Boss 層**

Boss 是**一次性的場景設計**，可學習性的顧慮小得多；而那裡正是最需要「打死一個 → 爆炸給分 → 立刻再開火 → 打死下一個」連鎖高潮的地方。**預設用 C，Boss 用 A。**

> **B 不採用**，但若 C 的「敵人死了還在（變成瓦礫）」在測試中讓玩家困惑，B 是安全的退路（代價是物理連結斷裂）。

- 過關：8 回合內把敵人 HP 打到 0 → 否則本局結束
- HUD：**充能條（持續長大的數字）**／**「每顆球約攻擊 N 次」**／本球連擊數／敵人 HP 條／剩餘回合／期待值計量條
- 基礎轉換率起始 **10%**（**從第一天就生效，不做解鎖式設計**）
- 攻擊形態（軸 D）：M0 只做「單體一擊」，M1 再加多段／擴散

> ⚠️ M0 就要讓「充能上限」是個**可調參數**（Inspector 可改），這樣才能用灰盒直接測試「每顆球 1 次」vs「每顆球 5 次」vs「每 5 顆球 1 次」的手感差異。**這是 17.8 第 2 條檢驗的前提。**

**M0 驗收（五條）**

1. **操作手感**：同一張盤面投 30 次，玩家是否能自己歸納出「力度 ↔ 路線」的對應並產生偏好？
   → 若否：先加磁力球與落點熱區顯示；再否 → 檢討是否改回 T1=(b)。
2. **數字循環**：玩家是否在 3 局內就理解「盤面賺分 → 充能 → 自動開火 → 傷害 → 打敵人」，並且**會為了打更高傷害而主動調整配球或選遺物**？
   → 若否：問題在軸 A 與軸 B 的比例，先調數值，不要急著加系統。
3. **充能上限的體感差異（17.8-2）**：把上限調成低／中／高三檔，玩家是否能**立刻**說出「攻擊變頻繁了」或「變大發了」？
   → 若否：軸 C 不成立，整個「高頻 vs 大傷」的流派設計要重新考慮。
4. **拿掉所有遺物還想再玩一局（17.8-4）**：若不想，**基礎玩法有問題，不要靠加內容掩蓋**。
5. **開火節奏**：一顆球開火 1 次 vs 5 次，哪個比較爽？**這個答案會決定 17.4.3 的曲線基準。**
